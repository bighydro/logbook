    Entities: the three profiles

    RFC 0037 gives the record five kinds of thing that recur across its lines: a person, an org, an idea, an asset and a place. Each is a canonical entity the owner confirmed, reviewed in one sitting (logbook review KIND) and disposed of with one command (logbook status). Three payload profiles carry what the owner said. All three are source manual: the owner said it, through a review or a command; no adapter writes one.

    Profile Says Written by Tier
    entity/v1 this is an org, an idea, an asset or a place, and these refs are it review KIND --accept / --name 2
    entity-review/v1 this observed thing is not that entity (the owner's no) review KIND --reject, people review --reject, places review --reject the highest of its evidence, at least 2
    status/v1 what the owner decided about an org, an idea, a place or an asset logbook status KIND ENTITY DISPOSITION 2

    The profiles are new and in draft with RFC 0037; they become frozen only by RFC 0031's process. The envelope does not change. The code is logbook/contrib/entities.py: one validator per profile, the dedupe keys, the tier rules and the readers.

    How a ref binds

    • A person binds through resolution/v1 (RFC 0006, frozen), and only there. An entity/v1 line for a person may give aliases; its refs must be empty.
    • An org, an idea, an asset and a place bind through entity/v1 only: its refs.
    • A resolution/v1 line of type company, the frozen word, is read as an org entity, and never rewritten. org is the kind; company is a legacy value; the Manifest is the shelf's name.
    • A ref resolves to the entity named by the last standing line that binds it, whichever profile.

    entity/v1

    kind entity, source manual, tier 2 for every kind. An entity/v1 line never cites a tier-3 line: a merchant match is bound as a merchant ref, a folded string, and the ledger is read at the page within its ceiling. at is when the owner said so; end is null.

    Field Type Req Meaning
    schema "entity/v1" MUST
    entity object MUST { type, id, registry }. type one of person, org, idea, asset, place; registry logbook. id: a UUIDv7 minted in this record for an org or an idea; the UUID its resolution minted for a person; the name places.json spells for a place; the id assets.json holds for an asset
    label string MUST the name the owner gave or accepted
    refs array of { kind, value } SHOULD what the line binds: RFC 0006's kinds (email, phone, handle, provider_id, device_id, domain, line) or repo, page, title, group, merchant, mmsi, icao24, registration, place. Empty for a person. A later line adds refs, never removes one
    aliases array of string MAY other spellings of the label
    keys object MAY the dedupe key the writer computed, under the kind (below)
    method string MAY owner
    evidence array of string MAY ids of the lines it was seen on; never a tier-3 line
    supersedes string MAY the entity/v1 line this replaces (a relabel)
    logbook_head hex sha256 MAY the head the proposal was read against
    extra object MAY what the kind needs and no line already holds (an idea's pitch)

    entity-review/v1

    One profile for every no (RFC 0035's shape, every kind). kind entity-review, source manual. Its tier is the highest tier of the evidence it cites and never under 2, a decision (SPEC §4); it may cite a transaction/v1 line, and is then tier 3. People review writes it for a person from now on; a people-review/v1 line is read as an entity-review/v1 of type person, forever. A place's no is a line too: places review --reject writes one, and state/places-review.json is a cache rebuilt from the lines; --migrate-rejects writes the pairs the file held from before 0.7 as lines, once.

    Field Type Req Meaning
    schema "entity-review/v1" MUST
    verdict string MUST different: the observed thing is not the entity. A same is a binding line, never this
    ref { kind, value } MUST the observed thing's strongest identifier: a person's email, phone or folded name; an org's domain, repo, group or merchant; an idea's page, repo or title; an asset's mmsi, icao24, registration or subject; a place's centre (lat,lon to six decimals)
    refs array of { kind, value } SHOULD its identifiers as the lines wrote them; a later observation matches ref or any of these
    observed array of string MAY the names it was seen under
    entity object MUST the canonical entity proposed, { type, id, registry }; for a proposal of a new entity (an org, an idea or an asset not yet minted, a place name) { type } alone, the name in label, and for a rejected blank no label either. A person's is always whole
    label string SHOULD the entity's label at the time, or the name the proposal gave
    method string MAY owner
    evidence array of string MAY ids of the lines the observed thing was seen on
    logbook_head hex sha256 MAY the head the proposal was read against
    raw_id, extra MAY the writer's: the proposal's id, its score and what matched

    A review reader never proposes the observed thing against the entity again while the line stands; retract it and the proposal returns. An org seen as a sailing club's chat group, not the yard:

    status/v1

    What the owner decided, at a point in time. kind status, source manual, and no money on the line: the ledger holds it. Its tier is the kind's (RFC 0037 §8): 3 for an org, whose dispositions describe a position in money (a passed at 2 among holds at 3 would say which is which), so the line may cite tier-3 evidence; 2 for an idea, a place or an asset, a decision about your own work, place or craft, which never cites a tier-3 line. A person has no status; a goal is reviewed by RFC 0036's review/v1. at is when the owner disposed; end is null.

    Kind Dispositions
    org hold, add, sell, let-go, exited, passed
    idea spark, exploring, build, built, killed
    place let-go
    asset sold, let-go
    Field Type Req Meaning
    schema "status/v1" MUST
    entity object MUST { type, id, registry }, type org, idea, place or asset
    label string SHOULD the entity's label at the time
    status string MUST one of the kind's dispositions; any other makes the line invalid
    reason string SHOULD; MUST for passed, let-go, killed the owner's words on why; for an org, the only place they are written
    note string MUST when reason is given, except for an org the id of the note/v1 line written just before this one with the same words; an org's line has none
    proposed_by string MUST dream when the owner disposed of a proposal, owner when unprompted
    proposal object MAY what the dream proposed, { status, score, because }
    since date MAY the local day it took effect when not the line's own day
    evidence array of string MAY ids of the lines the proposal rested on
    supersedes string MAY the standing status line this replaces
    logbook_head hex sha256 MAY the head the proposal was read against
    portfolio string MAY for an org, never another kind which portfolio holds the company, free text (Fund I); empty clears it

    Rules. The current status is the last standing line's; any status may follow any. A status equal to the standing one on the same local day is refused; on a later day it is written only with a new reason (the owner reaffirmed, and said why). status --reason "…" puts the owner's words in the line's reason. For an idea, a place or an asset it first writes one note/v1 line, tier 2, label status, the words as its text and the entity under extra.entity (never the disposition), then the status line, whose note names it, both under one hold of the writer lock (RFC 0037 §10.5), so the owner's words are on the day and in search. A pair written before the writer kept this order, the status line first and the note naming it under extra.status, is read the same. An org's reason stays on its tier-3 status line and is never a note: RFC 0010 fixes a note at tier 2 (MUST), and a reason about a company can name money, so a note would carry it wherever tier 2 crosses. No status writes a note above tier 2. status list and the status command's output read the reason from the status line, and status list --json names its note (note, null for an org). A place let go and an asset sold or let go close their registry entry with until, the line's local day: the entry in places.json or assets.json is never deleted (ADR 0018, rule 4).

    The portfolio (RFC 0037 §10.2, amended 15 October 2026). status org ORG DISPOSITION --portfolio "Fund I" names which portfolio holds a company, free text, its words collapsed, in the line's portfolio field; --portfolio "" writes it empty, which clears it. An org's portfolio is the field of its latest status line that carries it: a status without --portfolio leaves it as it stood, a retracted line counts for nothing, and an empty field clears it. Which portfolio holds a company is a position in money, so it rides on the org's tier-3 status line and never on its entity/v1 line, which is tier 2 and never cites tier 3; only an org's status takes one, and a portfolio given for an idea, a place or an asset is refused in one sentence with nothing written. A status equal to the standing one is written when it moves the portfolio (to another one, case and spaces aside, or to none), on the same day too; giving the portfolio that stands, however spelled, moves nothing and is refused as before, the refusal naming it. A line that repeats the standing status only to move the portfolio, with no new reason, is no reaffirmation: it carries since, the day the standing status took effect, so "hold since" and the stale flag stay where they were; it carries no reason of its own, so a mute ends with it. Give a new reason and it reaffirms, and both restart. status list org says each org's portfolio.

    Readers' rules, never lines (policy/entities.json):

    • Mute. A status line with a reason that answers a proposal of another disposition (the dream proposed let-go, the owner held, and said why) mutes proposals of that disposition for that entity for mute_days, 365 by default, while it is the current status. There is no "never" line.
    • Stale. A hold older than three years and an exploring older than two are stale (stale_days, {"hold": 1095, "exploring": 730}); status list says so.

    The orgs read back

    logbook show orgs is every org you named (RFC 0037 §11), under its current status: holding (hold, add, sell), exited, passed (the anti-portfolio, each with its reason in full), let go, then no status; within a heading the most recent touch first. A touch is a line that resolves to the org through one of its refs: a mail or a meeting with an address at its domain, a transcript one of its people spoke in, a page or an act on its code-host org, its group chat, its merchant. A row says the status and since when, its portfolio, the last touch and what it was, the people on its lines (the first two by days), how many documents (mails and repositories, as references) and stale when the status is one stale_days names and neither it nor a touch falls within that many days of today. Then the people who appear with more than one org: the co-investor graph. show orgs --portfolio "Fund I" keeps the orgs that portfolio holds, case and spaces aside, and the people across them; a portfolio that holds none says so and names the ones that hold some.

    logbook show org NAME is one org's page (RFC 0037 §7), the org named as status names one (a domain, a word of its name, its id): its refs, its status, its reason and its portfolio, every touch newest first, the people, who introduced whom where a mail's subject says so (Intro: Ines <> Liv), the documents and every status line with the portfolio it carried, the one in force marked and a retracted one said so. An org whose naming line was retracted stays while a status line names it, under that line's label (RFC 0037 §3.4 rule 3); two orgs of one label are told apart by their key. Both take --json; nothing is written.

    Money only with --money. A ledger line the org's merchant refs match is a touch like any other, so the last touch, the order and the stale flag are the same with --money or without; without it the shelf says only the ledger for it, with no merchant and no figure, and the page shows no ledger row. With --money the page adds the ledger's lines and its in, out and net per year, and the shelf each row's for --year (this year by default), derived at read time. No line of the org cites them.

    Tier 3 stays tier 3. An org's status line is tier 3, and its reason and its portfolio are on it; the page and the shelf read every line through a gate (the owner's terminal and logbook serve read every tier; a crossing, an exported site and the door read their policy's). Through a gate without tier 3 there is no status, no reason and no portfolio: every org is under no status, the shelf says how many status lines it may not show, and a portfolio asked for lists no org, the same for every portfolio; an org's page says only that it shows none, never how many it has, which would tell which orgs carry a decision. A person who is with an org only on a tier-3 line (a split payment) is no edge of the graph there; an edge is as high a tier as the lines it rests on.

    The ideas read back

    logbook show ideas is every idea you named (RFC 0037 §11), under its current status in the order build, exploring, spark, built, killed, then no status; within a heading the most recent touch first. A touch is a line that resolves to the idea through one of its refs, as review idea finds them: a Notion page under its root (a database row is its own root), an act on its repository or a link into it, a task or a call of its title. A row says the status and since when, the reason (the latest you gave, with its status and day when a later status replaced it: a killed idea that sparked again), the last touch, the words written this year (--year; the Notion deltas), the repositories, how many people it was discussed with and never their names, the days since its spark (its first touch), its latest titles, and stale when the status is one stale_days names (an exploring over two years) and neither it nor a touch falls within that many days of today.

    logbook show idea NAME is one idea's page (RFC 0037 §7), the idea named as status names one (a ref, notion:<id> or a repository, its id, its name, a word of it): its refs, its status and its reason, first said, every touch newest first, the people it was discussed with by name (an observed person not yet placed is counted, never named), its documents as references (its Notion pages with the titles above them and their word counts, its repositories with their README's versions), its title thread (the titles of its pages, tasks and calls), the words written by month and every status line, the one in force marked and a retracted one said so. Both take --json; nothing is written.

    What is never a touch. A line a bot made (extra.actor.type bot from sync notion, Bot from sync github) or an agent wrote (extra.machine), and a relations line (sync notion --relations-backfill), touch no idea, show no person and add no words; an agent on a call is no participant (the owner's decision of 14 October 2026). An act you made through a coding agent under your own account (sync github's extra.agent) is yours, and is a touch like any other. A page's body, a commit's message and a call's words are never shown: the record holds a page's digest and word count, and the page says only what a line already holds (a title, the titles above it, a count, a commit's first line).

    The type keeps a row out of the queue, never out of an idea. A Notion row whose Type is not Idea is never proposed by review idea; when you bound it to an idea yourself (an entity/v1 line with its page), its lines are that idea's touches like any other.

    The dedupe keys

    A key is what a writer looks up before minting, so a second sitting, a second machine or a re-run never mints the same thing twice. Folded: NFKC, case aside, whitespace collapsed.

    Kind Key, strongest first Example
    person email:, else phone: (E.164), else name: (words sorted) email:ola.nordmann@example.org
    org domain: (the registered domain), else repo-org: (host and org), else group:, else merchant: domain:nordmann-verft.example
    idea page:notion: (the root page), else repo: (host, owner, name), else title: (words sorted, articles out) repo:github.com/nordmann-verft/kiosk
    place place: (the name places.json spells) place:hytta på banken
    asset mmsi:, else icao24:, else registration: (hyphens out), else subject: mmsi:970123456

    The registered domain is the public suffix and one label, read from the suffixes the code carries and public_suffixes in policy/entities.json; the names RFC 2606 reserves count as suffixes, so in the synthetic record post.verft.example.org is the org verft.example.org and example.org, a public mail provider, names nobody's org.

    policy/entities.json

    One setting, read each run, never a line. Absent is the defaults.

    {"public_mail_providers": ["…"], "public_suffixes": ["…"], "code_hosts": ["github.com", "gitlab.com", "codeberg.org"],
 "merchant_min_lines": 3, "title_min_lines": 2, "registration_min_flights": 3,
 "mute_days": 365, "stale_days": {"hold": 1095, "exploring": 730},
 "idea_rows": {"property": "Type", "value": "Idea"}}

    The provider list extends the default the code carries (RFC 0037 §4.6); the owner's own domains are never an org. The thresholds are hypotheses, as policy/stays.json's constants are. idea_rows is the select of a Notion database row and the option that make the row an idea for review idea (case aside; the owner's decision of 14 October 2026): a row of another type, and a page under it, is never proposed, and a page that is no row is proposed as before.
