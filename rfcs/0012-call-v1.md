# RFC 0012 — payload profile `call/v1`

Status: draft · 2026-09-30 · comment period: two weeks

One call in a call log — placed, answered, or missed — from any source that keeps one: the phone's own call history, FaceTime, a VoIP app that registers with it. The line records what the log stored: who was on the other end as the log spelled it, which way the call went, whether it connected, and for how long. It carries no one's words: a call log has no body.

## Line

`kind` MUST be `call`. `tier` SHOULD be 1 (SPEC §4): a call record is metadata about the owner's own time, like a calendar attendee, and no more identifying than an `event/v1` attendee ref. `at` is the call's start as the source stored it; `end` is `at` plus `duration_s` when the call was answered, else null. `source` is the adapter: `ios-calls`, …

## Payload

| Field | Type | Req | Meaning |
|---|---|---|---|
| `schema` | `"call/v1"` | MUST | |
| `raw_id` | string | MUST | the source's own stable id for the call (iOS `ZUNIQUE_ID`), else the row's stable id in the store. The dedupe key: re-importing the same store appends nothing |
| `direction` | string | MUST | `incoming` or `outgoing` |
| `answered` | boolean | MUST | true when the call connected; a missed, declined or unanswered call is false |
| `duration_s` | integer | MUST | seconds connected, as the source counts them; 0 when not answered |
| `counterparty` | object | SHOULD | the other end as the source identifies it, source-native (RFC 0006 `ref` shape): `{ kind, value }` with `kind` one of `phone`, `email`, `handle`. Absent when the source has no address (a withheld number) |
| `service` | string | SHOULD | which service carried it, as the source names it: `cellular`, `facetime`, `facetime-audio`, `whatsapp`, … |

Anything else the source reports MAY be kept under `extra`.

## Rules

1. One line per call the source stores. A conference call, a call that was transferred, a call waiting: whatever the source counts as one record is one line; the log does not reconstruct the conversation.
2. `counterparty` is never resolved here. Mapping `+4790…` to a person is a `resolution/v1` line (RFC 0006), and one resolution of a number covers the address book, the chats and the calls. A caller-id name the source itself displayed MAY be kept under `extra`, as text the source showed, never as an identity.
3. `answered` is the source's own flag, not derived from `duration_s`: a call that connected and dropped at once is answered with duration 0.
4. Timestamps are the source's. The adapter converts the source's epoch to UTC and does not "correct" it. Sentinel-dated rows (before 1900) are the store's placeholders, not calls, and are skipped and counted (as RFC 0009 rule 4).
5. `service` is what the source says, spelled as one lower-case token; the source's own raw value MAY be kept under `extra`. A source that does not say gives no `service`.

## Example (synthetic)

```json
{"at":"2026-03-02T15:04:10Z","end":"2026-03-02T15:11:35Z","tz":"Europe/Oslo","source":"ios-calls","kind":"call","tier":1,
 "payload":{"schema":"call/v1","raw_id":"3B1F8E2A-6C4D-4F7B-9A0E-2D5C8B1F4A7E","direction":"incoming","answered":true,
 "duration_s":445,"counterparty":{"kind":"phone","value":"+4790000001"},"service":"cellular"}}
```

## Notes

- **Why tier 1.** A call record says that the owner was on the phone with a number for seven minutes. That is the owner's own time, the same class of fact as a calendar entry with one attendee (RFC 0009), and it carries nothing anyone said. A voicemail or a recording of the call would be another line (`transcript/v1`, tier 2 by RFC 0004; the reference adapters write 3), never this one.
- **Missed calls are lines.** The phone rang; that is a fact about the day even when nobody answered. `answered` false, `duration_s` 0, `end` null.
- **A call is not a message.** `message/v1` (RFC 0008) is for words in a chat; a call has a span and no body. An engine that wants "contact with Ola this week" reads both by the same `counterparty`/`sender` ref.
