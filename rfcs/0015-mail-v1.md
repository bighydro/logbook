# RFC 0015 — payload profile `mail/v1`

Status: draft · 2026-10-01 · comment period: two weeks

One email message — sent or received — from any source that keeps a mailbox: a Google Takeout mbox export, a Maildir, a later live IMAP puller. Email is not `message/v1` (RFC 0008): it has a subject, a thread, many recipients, labels and attachments, and one message reaches several mailboxes. The line records what the mailbox stored: the headers that identify the message and the people on it, the body as plain text, the attachments by digest. No sentiment, no extracted tasks, no resolved names.

## Line

`kind` MUST be `mail`. `tier` SHOULD be 2 (SPEC §4: personal mail is tier 2); an import MAY set another tier for the whole run (`--tier`), never per message. `at` is the message's `Date` header in UTC; `end` is null. `tz` is the record's zone: a `Date` header carries a numeric offset, not a zone name, so the header's own spelling is kept in `date` and the envelope's `tz` says nothing about where the sender was. `source` is the adapter: `mail`.

## Payload

| Field | Type | Req | Meaning |
|---|---|---|---|
| `schema` | `"mail/v1"` | MUST | |
| `raw_id` | string | MUST | the `Message-ID` header without its angle brackets, prefixed by the account and a colon when the source knows which mailbox held the message (`kari.nordmann@example.org:<id>`); a message with no `Message-ID` gets `sha256:<hex sha256 of its bytes>`. The dedupe key: re-importing the same export appends nothing, and a live puller of the same mailbox dedupes against the export (ADR 0017) |
| `message_id` | string | SHOULD | the `Message-ID` header without its angle brackets; absent when the message has none |
| `thread` | string | MUST | the id of the thread this message is in: the first entry of `References`, else `In-Reply-To`, else the message's own id (its `raw_id` when it has no `Message-ID`). Every message of one thread names its root |
| `from` | object | SHOULD | the sender as the header spells it: `{ email, name? }`, `email` lower-cased, `name` the display name as written, never a resolution. Absent when the header is missing or has no address |
| `to`, `cc`, `bcc` | array | MAY | the recipients of each header, in header order, each `{ email, name? }` as `from`; a header that is absent or empty gives no field |
| `subject` | string | MAY | the `Subject` header, decoded, whitespace folded; absent when empty |
| `date` | string | SHOULD | the `Date` header as RFC 3339 with the header's own offset kept (`2026-03-02T11:15:00+01:00`); `at` is the same instant in UTC. Absent when the header is missing and `at` came from the mbox separator |
| `direction` | string | MUST | `sent` when `from.email` is one of the owner's addresses, else `received`. The owner's addresses are `owner_emails` in `logbook.json` plus the account of the import when one is given; with none configured every message is `received` |
| `labels` | array of string | MAY | the mailbox's own labels or folders as it spells them (Gmail's `X-Gmail-Labels`, split on commas); absent when it has none |
| `body` | string | MAY | the body as plain text: the `text/plain` part; else the `text/html` part with tags stripped and entities decoded (a minimal stripper, no external library); absent when the message has neither. A producer MAY read only the first part of a long body (the reference reads at most 64 KB of the part) and then says so with `extra.body_truncated` |
| `size` | integer | MUST | the length in bytes of the message as the source stored it, headers included |
| `attachments` | array | MAY | one object per attachment part, in message order: `{ filename, media_type, bytes }` — the part's file name, its media type (`media_type`, never `content_type`) and its decoded length — and, only when the producer decoded the part, `sha256` and `path` (`attachments/<sha256>`), the SPEC §1.1 reference shape, `path` only when the bytes are in the record's store. Absent when the message has none |
| `account` | string | MAY | the mailbox address the message was read from, when the source knows it |

Anything else the source reports MAY be kept under `extra`: Gmail's `X-GM-THRID` as `extra.gmail_thread_id`, `In-Reply-To` and `References` as `extra.in_reply_to` and `extra.references` (bare ids), the header's charset trouble as `extra.decoding_errors`, the body's origin as `extra.body_from` (`html` when stripped from HTML), a body cut short as `extra.body_truncated`.

## Rules

1. One line per message the source stores. A message the owner received in two mailboxes is two messages: they have different labels and, with the account in the `raw_id`, different ids. A message with no `Message-ID` is still a line, keyed by its own bytes and counted (`no_message_id`); nothing is skipped silently.
2. `from`, `to`, `cc` and `bcc` are never resolved here. `{ email, name }` is the same identity the `resolution/v1` ref `{ kind: "email", value }` names (RFC 0006), so one resolution of an address covers the calendar, the transcripts and the mail. `name` is the header's display name, kept so a reader has something to show before any resolution exists.
3. `thread` groups lines; what a thread was *about* is an engine's judgement. A reader joins on `thread`, never on `subject`.
4. The body is text. An HTML-only message is stripped to its text so the line is readable and searchable, and `extra.body_from` says so; the HTML itself is not kept (a reader that needs it re-reads the export). A body the source could not decode is decoded with replacement characters and flagged `extra.decoding_errors`, never dropped.
5. Attachments are named and sized whether or not the bytes are read. A producer that never decodes them (the reference, by default: an export is mostly attachment bytes) records `filename`, `media_type` and `bytes` alone; one that decodes them records `sha256` too, and an import stores them in the §1.1 store only when asked (`--attachments`), which is when the reference decodes them. A line whose attachment has no `path`, or no `sha256`, refers to bytes the record does not hold, which is not an error; the export still has them. The same attachment sent twice is one file in the store.
6. Timestamps are the source's. `at` is the `Date` header converted to UTC, never corrected; a message whose `Date` is missing or will not parse takes the mbox separator's date (an mbox has one) and has no `date` field; one with neither is skipped and counted (`skipped_no_date`).
7. `size` counts the message as stored, so a reader can tell a one-line reply from a newsletter without reading either.

## Example (synthetic)

```json
{"at":"2026-03-02T10:15:00Z","end":null,"tz":"Europe/Oslo","source":"mail","kind":"mail","tier":2,
 "payload":{"schema":"mail/v1","raw_id":"kari.nordmann@example.org:a1b2c3@mail.example.org",
 "message_id":"a1b2c3@mail.example.org","thread":"9f8e7d@mail.example.org",
 "from":{"email":"ola@example.org","name":"Ola Nordmann"},
 "to":[{"email":"kari.nordmann@example.org","name":"Kari Nordmann"}],
 "subject":"Re: Mooring for the weekend","date":"2026-03-02T11:15:00+01:00","direction":"received",
 "labels":["Inbox","Important"],"body":"Photos attached. The east berth is free from Friday.\n",
 "size":48213,"account":"kari.nordmann@example.org",
 "attachments":[{"filename":"berth.jpg","media_type":"image/jpeg","bytes":41002}],
 "extra":{"gmail_thread_id":"1795123456789012345","in_reply_to":"9f8e7d@mail.example.org",
   "references":["9f8e7d@mail.example.org"]}}}
```

## Notes

- **Why not `message/v1`.** A chat message has one chat and one sender; an email has a thread, a subject, several recipients and labels per mailbox, and it can be a megabyte of HTML around three lines of text. Forcing it into `chat` and `text` would lose the recipients and the thread, which are the parts an engine asks about ("who was on that thread in March").
- **Why the account is in `raw_id`.** A `Message-ID` is global, so the same message in two of the owner's mailboxes would otherwise be one line and the second mailbox's labels would be lost. The price is that an export imported without an account and the same mailbox pulled live with one do not dedupe; an import of a mailbox whose address is known SHOULD say so (`--account`).
- **Why the body is in the line and the attachments are not.** The body is what the message said, and a line is meant to carry that. An attachment is a file (SPEC §1.1): binary, often large, often the same file sent many times. It is also most of a mailbox by bytes, which is why a producer need not decode it to name it: the length of a base64 part is known from its text, and the digest can wait until the owner asks for the bytes.
- **Why tier 2.** Personal mail is named in SPEC §4. A whole import can be lowered or raised (`--tier`), for a mailbox that is all newsletters or all medical, but the tier is never decided per message by the adapter: it does not read the message for that.
