# RFC 0010 — payload profile `note/v1`

Status: draft · 2026-09-18 · comment period: two weeks

Something the owner wrote for themselves: a sentence typed at the command line, a note in a notes app, a journal entry. Not a message (it has no recipient) and not a transcript (nobody spoke). This is the profile `logbook add "<text>"` has written since v0.1; this RFC writes it down and extends it for imported notes without changing what `add` produces.

## Line

`kind` MUST be `note`. `tier` MUST be 2 (SPEC §4: notes). `at` is when the note was written — for an imported note, its creation time; `end` is null. `source` is `manual` for the owner's own command, otherwise the adapter: `ios-notes`, `obsidian`, …

## Payload

| Field | Type | Req | Meaning |
|---|---|---|---|
| `schema` | `"note/v1"` | MUST | |
| `text` | string | MUST | the body, plain text, verbatim |
| `title` | string | MAY | the note's title if the source has one distinct from the body |
| `raw_id` | string | MAY | the source's stable id for the note, suffixed with its modification time (see rule 2), e.g. `"<uuid>@2026-03-04T10:15:00Z"`. Absent for `manual` |
| `modified_at` | RFC3339 | MAY | the source's last-modified time |
| `folder` | string | MAY | the source's folder or notebook name |
| `attachments` | array | MAY | `[{ sha256, path, bytes, media_type }]` per SPEC §1.1 |
| `supersedes` | string | MAY | id of the earlier line for the same note |

Anything else the source reports MAY be kept under `extra`.

## Rules

1. `logbook add "<text>"` writes exactly `{ "schema": "note/v1", "text": "<text>" }` with `source: manual`, `tier: 2`, and `at` = now unless `--at` is given. This is unchanged from v0.1 and is what the conformance sample contains.
2. Notes are edited over time, and the log is not. An imported note is a snapshot: the adapter's `raw_id` includes the modification time, so the same note imported again after an edit is a *new* line (the dedupe key differs), carrying `supersedes` = the earlier line's id. Readers show the latest by `supersedes`; the earlier text is still in the record.
3. Rich text is flattened to plain text by the adapter; formatting the source can't round-trip is lost on purpose. Checklists become lines beginning with `[ ]` / `[x]`.
4. A note is the owner's words. Text pasted into a note from elsewhere is still `note/v1`; the log does not guess provenance.

## Example (synthetic)

```json
{"at":"2026-03-04T21:10:00Z","end":null,"tz":"Europe/Oslo","source":"manual","kind":"note","tier":2,
 "payload":{"schema":"note/v1","text":"Decided: keep the boat one more season."}}
```

and an imported one:

```json
{"at":"2026-02-11T07:55:00Z","end":null,"tz":"Europe/Oslo","source":"ios-notes","kind":"note","tier":2,
 "payload":{"schema":"note/v1","raw_id":"5F1C…@2026-02-12T18:20:00Z","title":"Tromsø move","text":"Boxes: 14. Van booked for the 20th.\n[x] cancel gym\n[ ] forward mail","modified_at":"2026-02-12T18:20:00Z","folder":"Notes"}}
```

## Notes

- **Why not `decision/v1`.** A decision is a note the owner later calls a decision. Marking it is an engine's or the owner's act — a `resolution`-style line pointing at the note — not a different profile at write time.
- **Reminders and tasks** are not notes: they have a due date and a done state. They wait for `task/v1`.
