# RFC 0016 — payload profile `task/v1`

Status: draft · 2026-10-01 · comment period: two weeks

Something the owner meant to do: a to-do in Google Tasks, a reminder in Apple Reminders, an item in TickTick or Things. Not a note (RFC 0010: a task has a due date and a done state) and not an event (RFC 0009: it has no span on the calendar). The profile is written for every task app at once: the fields are the ones they all keep, spelled one way, and what one app keeps and another does not goes under `extra`.

## Line

`kind` MUST be `task`. `tier` MUST be 2 (SPEC §4: the owner's own words). `at` is the task's creation time when the source keeps it (Apple Reminders, TickTick), else the snapshot's own time — the task's last modification (Google Tasks keeps no creation time); `end` is null. `source` is the adapter: `google-takeout`, `apple-reminders`, `ticktick`, …; `tz` is the record's zone.

## Payload

| Field | Type | Req | Meaning |
|---|---|---|---|
| `schema` | `"task/v1"` | MUST | |
| `raw_id` | string | MUST | the source's stable id for the task, suffixed with `@` and its modification time (rule 2), e.g. `"aGVsbG8@2026-03-04T12:10:00Z"`; prefixed by the app when the source's ids are not global (`keep:`, `reminders:`) |
| `title` | string | MUST | the task as the owner wrote it; a task with no title is skipped and counted |
| `status` | string | MUST | `open`, `done` or `cancelled`. Google's `needsAction`/`completed`, Reminders' `completed` flag, TickTick's `0`/`2`/`-1` all map to these three |
| `due` | string | MAY | when it was due: `YYYY-MM-DD` when the source keeps a day only (Google Tasks always; a Reminder with no time), else an RFC 3339 instant in UTC |
| `completed_at` | RFC3339 UTC | MAY | when it was marked done; absent while `status` is `open` |
| `list` | string | MAY | the list, project or folder the task is in, as the source names it |
| `notes` | string | MAY | the task's notes or description, plain text, verbatim |
| `parent` | string | MAY | the `raw_id` prefix (the source id, without the `@` suffix) of the task this one is a subtask of |
| `priority` | string | MAY | `low`, `medium` or `high`; absent when the source has none or it is the default. Reminders' 1–4/5/6–9 and TickTick's 1/3/5 map to these |
| `tags` | array of string | MAY | the source's tags, as it spells them (TickTick; Reminders' hashtags) |
| `recurrence` | string | MAY | the rule as RRULE text (RFC 5545), as `event/v1` keeps it; occurrences never expanded |
| `modified_at` | RFC3339 UTC | MAY | the source's last-modified time; the same instant the `raw_id` suffix spells |
| `url` | string | MAY | a link the task carries |
| `supersedes` | string | MAY | id of the earlier line for the same task |

Anything else the source reports MAY be kept under `extra`: Google's `hidden` (done and cleared from the list) and `deleted`, its `links`, a position, Reminders' flagged state, TickTick's project colour.

## Rules

1. One line per task the source holds, subtasks included: a subtask is its own line with `parent`, never folded into the parent's `notes`.
2. Tasks change and the log does not. A task is a snapshot (as RFC 0010 rule 2): the `raw_id` ends in the modification time, so the same task exported again after it was ticked off is a *new* line and an unchanged one appends nothing. The latest line for a source id is the task's current state; a reader that lists open tasks takes, per source id (the `raw_id` before `@`), the line with the newest suffix. `supersedes` is set when the adapter can find the earlier line.
3. `status` is one of three words whatever the app calls them. An app with more states (TickTick's "won't do", Things' "someday") keeps its own word under `extra.status`.
4. A day-only `due` is a date, never a midnight instant: Google Tasks exports `2026-03-05T00:00:00.000Z` for "the 5th", and writing that as an instant would put the deadline at 01:00 Oslo time on the 5th, which is not what the owner meant.
5. A deleted task is still a line (`extra.deleted: true`): the owner wrote it, and the record keeps what was written. A task with no title is not a line.

## Example (synthetic)

```json
{"at":"2026-03-04T12:10:00Z","end":null,"tz":"Europe/Oslo","source":"google-takeout","kind":"task","tier":2,
 "payload":{"schema":"task/v1","raw_id":"aGVsbG8tcm9wZQ@2026-03-04T12:10:00Z","title":"Buy the long rope",
 "status":"done","due":"2026-03-05","completed_at":"2026-03-04T12:10:00Z","list":"My Tasks",
 "notes":"30 m, 12 mm. Ask at the chandlery on Storgata 1.","modified_at":"2026-03-04T12:10:00Z",
 "extra":{"hidden":true,"links":[{"type":"email","description":"the quote","url":"https://mail.example.org/u/0/#inbox/abc"}]}}}
```

## Notes

- **Why not `note/v1` with a checkbox.** RFC 0010 rule 3 writes a checklist *inside a note* as `[x]` lines; that is a note that happens to contain a list. A task app's item is addressed on its own — due, done, moved between lists — and a reader asking "what was open on the 4th" needs fields, not a regex over note bodies.
- **Why `at` is the modification time for Google Tasks.** The export has no creation time. The alternative, a fixed epoch, would put every task on one day; the modification time at least puts a done task on the day it was done and an open one on the day it was last touched. Apple Reminders and TickTick keep the creation time, and the same profile carries it.
- **Why three statuses.** Every task app has open and done; cancelled is the one extra state that changes what a reader should do with the task (not nag). Anything finer is the app's own vocabulary.
