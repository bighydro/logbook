# RFC 0042 — Hold: the census, the shelf, the sweep

Status: draft · 2026-10-17 · comment period: two weeks · builds nothing beyond the three censuses of §2 (`logbook lab hold census`, docs/hold.md); every profile below is a proposal, none is written by any code · builds on RFC 0034 (the signed day), RFC 0036 (drafts) and SPEC §4 (tiers) · proposes to amend RFC 0037 (entities) §3.2, §8 and §10 with a fifth type, `item`, if it is adopted (§3, §4)

The record says what happened. It does not say what the owner **holds**: the forty thousand files on
two disks and a Drive, the hundred apps, the three hundred senders who mail every month, the boxes in
the loft and the things in them. Each of these asks for attention, a little, every time it is seen
and not decided. Hold is the layer that gives each thing **one place** and **one fate**, so that the
attention it costs falls, and says with **one number** how much is left.

Hold is built in the order the owner can trust it: first a census that only counts (§2, built), then a
shelf that only names places (§5), then proposals that only propose (§6), and only then a weekly act of
the owner's that says what was decided (§7). Nothing in Hold ever moves, renames or deletes a thing on
its own. A fate the owner chose may later be carried out by a tool the owner runs, and that tool is
not in this RFC.

## 1. Words

- An **item** is one thing the owner holds, of one **sort**: `file`, `drive-file`, `app`, `sender`,
  `box` or `object` (§3).
- A **census** is a count of one sort of item from one road (a folder walk, the record's mail lines,
  the record's Drive lines), written as a local report and never as a line (§2).
- A **fate** is what the owner decided for an item (§4).
- The **shelf** is the one canonical place of each kept item (§5).
- **Stow** is the set of fates the dream or a rule proposes; a proposal is never a line (§6).
- The **sweep** is the owner's weekly signed reading of what was decided, the twin of the signed day
  (§7).
- **Weight** is one number for the attention the held things still cost (§8).

## 2. The census (built: Hold v0)

Three censuses run today, in the lab, as reports (`docs/hold.md`):

| Census | Reads | Counts |
|---|---|---|
| `files PATH…` | the folders named, read-only, never a link, never a system or Claude folder, never the record | files and bytes by type, extension and year; duplicates by SHA-256 of the bytes; the 50 largest; folders untouched for two years |
| `senders` | the record's `mail/v1` lines (RFC 0015) | senders by count and last seen; never answered (no mail to the address, no reply in its threads); newsletters by `List-Unsubscribe` when a line holds it |
| `drive` | the record's Drive lines (`event/v1`, source `drive`) | files by type, folder and last activity; untouched for two years; shared; trashed |

Rules the census keeps, and every later part of Hold keeps with it:

1. **Read-only.** No line is appended, and nothing in a walked folder is written, moved, renamed or
   deleted. The census's own report, under `state/hold/` in the record folder, is the only thing it
   writes.
2. **Names stay local.** A file's name, a folder's, a sender's address are in the report on the
   owner's disk and nowhere else: never on stdout, never in a line, so never in a crossing.
3. **No network.** A census of a remote thing reads what the record already holds of it.
4. **Tiers.** A report takes the highest tier it read; lines above `--tier` are left out and counted.
   The files report is tier 3, because a file name can say anything.

## 3. The item, under RFC 0037

An item is an entity of RFC 0037 of a new type, `item`, so that it is reviewed, named and given a
status by the same mechanism as an org or an asset (one road: `entity/v1`), and the owner's no is
one `entity-review/v1` line. The **observed** item is a derived row, keyed by the strongest
identifier of its sort; the **canonical** item exists because the owner accepted it.

| Sort | Strongest identifier (`refs[].kind`) | Seen by |
|---|---|---|
| `file` | `sha256` (the bytes; two copies are one item with two places) | the files census |
| `drive-file` | `drive` (the Drive id) | the Drive lines |
| `app` | `bundle` (`com.example.app`, a package name) | a future census of this Mac and the phone backup |
| `sender` | `domain` for a sender that is an org (a newsletter), else the person's `email` through `resolution/v1` | the mail lines |
| `box` | `label` (the owner's own label on the box, `LOFT-03`) | the owner, by hand |
| `object` | `label`, or an asset's `mmsi`, `registration` | the owner; an asset of ADR 0018 is an object already |

A sender is the one sort that is not new: a newsletter is an org of RFC 0037 (its `domain`), a person
is a person. Hold adds the fate to them, not a second identity.

This is an amendment of RFC 0037, proposed here and made only if this RFC is adopted: §3.2 gains the
type `item` and the ref kinds above (`sha256`, `drive`, `bundle`, `label`), §8 its tier, and §10 its
status values (§4). An `item` entity line is tier 2: its label is the owner's words about what they
own, which SPEC §4 puts with the notes. Like every `entity/v1` line it never cites a tier-3 line
(RFC 0037 §3.1). An item's label is a
name the owner chose (`Tax papers 2020`), never the file name the census found, so a canonical item
carries no file name into the chain. Whether an item line may carry a path at all is open (§10, Q1).

## 4. Fates

A fate is a `status/v1` line of RFC 0037 on an item, with these values:

| Fate | Means |
|---|---|
| `keep` | it stays, on its shelf (§5) |
| `archive` | it stays, out of sight: cold storage, an archive disk, an archive label |
| `let-go` | the owner will remove it; the record keeps that it was decided, not that it was done |
| `give` | it goes to someone (an object, a box) |
| `sold` | it was sold (an object), RFC 0037's value for an asset, not its org value `sell` |
| `done` | the fate was carried out, by the owner; a later line, never inferred |

The fate is the owner's answer, as every status is (RFC 0037 §10): proposed, never written by a rule.
A `let-go` carries its reason, as RFC 0037 requires of `let-go` for every type. The word **hold**
names this layer only: RFC 0037's org status `hold` (keep the stake) is another word, and no fate of
an item is called `hold`; `keep` is.
A fate never moves a thing. `let-go` followed by `done` is the owner's word that the thing is gone;
the record cannot check it, and does not try.

## 5. The shelf

The shelf gives each kept document **one canonical place**: one folder, one Drive path, one box. It is
a registry beside `places.json` and `assets.json`, `shelf.json`, the owner's own file: a shelf name
(`Papers/Tax`, `Loft/Box 3`) to where it is on which device or in which room. A kept item names its
shelf in its `keep` status (`extra.shelf`). Two copies of one file (one `file` item, two places) are a
question with one good answer: the copy on its shelf is the item, the other a duplicate whose fate is
asked (§6).

`shelf.json` holds places, not things: it never lists a file, and nothing in it leaves the machine.

## 6. Stow: proposed fates

Stow is what the dream (RFC 0036) and a few plain rules propose: a duplicate outside its shelf →
`let-go`; a folder untouched for two years → `archive`; a newsletter never opened and never answered →
`let-go` (the sender's fate, an unsubscription the owner does); a Drive file trashed → `done`. A
proposal is a row of a derived table, shown in the review (`review item`, RFC 0037's one review), and
becomes a line only when the owner answers. A proposal names the rule that made it. A `draft/v1` may
explain a batch of proposals; it never holds one.

## 7. The sweep

The sweep is a weekly signed object, the twin of the signed day (RFC 0034): `sweep/v1`, one line,
the owner's reading of a week of Hold, written only by the owner's act (`logbook hold sweep
sign`, a door tool named under `write` like `sign_day`).

| Field | Meaning |
|---|---|
| `week` | the ISO week, `2026-W42` |
| `decided` | counts of fates written that week, by fate and sort |
| `done` | counts of fates carried out |
| `weight` | §8, at the head the owner read |
| `census` | per census run that week: its sort, when, and the SHA-256 of its JSON report, never the report |
| `logbook_head` | the head the owner read |

Its tier is the highest tier of what it was made from (SPEC §4: derived material takes the highest
tier it read): a week whose counts came from the senders census (tier-2 mail) is tier 2, one that
read the files census (tier 3) is tier 3. Whether a sweep of counts and digests alone may be lowered
to tier 1, so that it crosses where a signed day crosses, is open (§10, Q7). A sweep re-signed
keeps the confirmations of the one before, as a re-signed day does (RFC 0034, as amended).

## 8. Weight

Weight is one number for the attention load: the items without a fate, each counted by its sort's
cost, plus the items whose fate is `let-go` and not yet `done`, at half. A starting set of costs, for
the owner to change in `policy/hold.json`: a sender that wrote in the last 30 days 3, a duplicate set 1,
an untouched folder 1, an app 2, a box 5, an object 1. Weight is derived at the head, never stored but
in a sweep; its trend week over week is the measure Hold is judged by. Whether one number can carry
this without hiding what matters is open (§10, Q5).

## 9. Privacy

- File names, folder names and addresses stay in the reports under `state/hold/` (mode 0600) and in
  the owner's own `shelf.json`. A line carries an item's label, its sort, its identifier's digest
  and its fate.
- A `file` item's `sha256` ref is the digest of bytes the owner holds; whether a digest of a private
  file may sit in a tier-1 line is open (§10, Q2).
- The reports are not sealed today, even in a sealing record (SECURITY.md).

## 10. Open questions

1. **Paths in the chain.** May an `item` line carry the path of its shelf copy (tier 2, sealed), or
   only its label, the path staying in `shelf.json`? Recommended: label only.
2. **The digest of a private file in a line.** A `sha256` ref proves the owner held those bytes; to
   anyone holding the same file it says so. Recommended: the ref is salted per record, as RFC 0039
   salts a day's commitment.
3. **Sealing the reports.** Should `state/hold/*` be sealed to the record's recipients when it has
   them? Recommended: yes, before Hold leaves the lab.
4. **Newsletters.** `mail/v1` keeps no `List-Unsubscribe`. Add `extra.list_unsubscribe` (a boolean,
   or the header's `mailto`/`https` kinds, never the URL) to the mail adapters? Recommended: a
   boolean, by an amendment of RFC 0015.
5. **One number.** Is Weight one number, or one per sort with a total? Recommended: one, with the per-sort
   parts shown beside it on the sweep.
6. **The sweep's cadence.** Weekly, signed on the week's last day like a day at its day start; or on
   demand? Recommended: weekly, never more often.

7. **A sweep at tier 1.** Counts and digests say how many, never what; may the owner lower a sweep to
   tier 1 by a policy entry? Recommended: no; a sweep stays at the
   tier of what it read, and a tier-1 summary, if wanted, is a separate line.
8. **Cloud files.** A file whose bytes are in iCloud or OneDrive is counted, never read (reading it
   would fetch it). Should a later census ask the provider for its digest, where one is offered,
   behind `sync`? Recommended: only behind a command that says it opens a connection.

## 11. What this RFC does not do

It writes no line and defines no frozen profile: `entity/v1` with type `item`, the fates, `sweep/v1`,
`shelf.json` and `policy/hold.json` are proposals for comment. It never moves, renames or deletes a
thing, and no later part of it may without a tool the owner runs by name.

The profiles here have no JSON Schema and no synthetic example yet, as `rfcs/README.md` asks of a
profile proposed for adoption: they come with the amendment of RFC 0037 when the owner decides the
open questions.
