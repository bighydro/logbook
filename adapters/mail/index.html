    Mail

    One line per message. logbook add mail reads a Google Takeout Mail/ export — All mail Including Spam and Trash.mbox, twenty gigabytes for a mailbox that has been running for fifteen years — or any mbox file or folder of them; logbook sync mail reads the same mailbox live over IMAP (below), and logbook sync gmail a Gmail mailbox over the Gmail API on the one Google key (below). Each writes one mail/v1 line per message (RFC 0015): who, when, the subject, the thread, the labels, the body as text, the attachments by name and size. Tier 2 by default. All three write the same line for the same message (but for Gmail's tab, which IMAP cannot say: below), and each, before it writes, skips a message the record already holds by its Message-ID from any of the three (One email, one line).

    logbook add mail ~/Takeout/Mail --account you@example.org --skip-labels Spam,Trash   # the whole export
logbook add mail ~/Takeout/Mail/"All mail Including Spam and Trash.mbox" --since 2024-01-01
logbook add mail inbox.mbox --only-labels Inbox,Sent --attachments     # keep the attachments' bytes too
logbook add mail inbox.mbox --dry-run                                   # count, write nothing
logbook add mail inbox.mbox --restart                                   # from the first byte again

    What a message becomes

    Field What it holds
    at, date the Date header in UTC, and as written with its own offset; a message with no readable Date takes the mbox separator's time and has no date (counted)
    raw_id the Message-ID without its brackets, as the header spells it, <account>: first when --account names the mailbox; no Message-ID (or one of brackets alone, <>) → sha256:<digest of the message> (counted). The store's dedupe key: the same export twice appends nothing
    message_id the Message-ID normalised: whitespace around it and its brackets off, the domain part (after the last @) lower-cased, the part before it as written. The key the three roads share (One email, one line)
    thread the root of References, else In-Reply-To, else the message's own id; Gmail's own thread id is extra.gmail_thread_id
    from, to, cc, bcc {email, name?} as the headers spell them, the address lower-cased, the display name as written
    direction sent when the sender is one of owner_emails in logbook.json or the --account, else received
    labels Takeout's X-Gmail-Labels, split on commas
    body the text/plain part, else the text/html part stripped to text (extra.body_from: html); read from at most 64 KB of the part, a longer one cut and flagged extra.body_truncated
    size the message's length in bytes as the export stores it
    attachments one {filename, media_type, bytes} per attachment part, in order; with --attachments also sha256 and path in the SPEC §1.1 store
    extra.gmail_category Gmail's inbox tab, primary, social, promotions, updates or forums, from the Category … label in X-Gmail-Labels; absent when none (below)
    extra.list only for a message from a mailing list: unsubscribe, one_click and id, never a link (below)

    The tab and the list headers

    Since 20 October 2026 (RFC 0015, amendment of that day) every road keeps two more facts under extra, never in the payload's own fields, so labels, raw_id and every dedupe key are what they were:

    • extra.gmail_category, Gmail's inbox tab: primary, social, promotions, updates or forums. A Takeout names it among X-Gmail-Labels (Category Personal is the Primary tab, then Category Social, Category Promotions, Category Updates, Category Forums, in any case); the label stays in labels as Takeout spells it. sync gmail reads it from the API's CATEGORY_* label, which stays out of labels as before. sync mail never writes it: IMAP's X-GM-LABELS does not carry the tabs, and the source does not search each message to find out. A message whose labels name no tab has no key.
    • extra.list, only when the message carries a list header: {"unsubscribe": true} for List-Unsubscribe, "one_click": true when List-Unsubscribe-Post is there too, and "id" the list's id alone (letters.example.org from List-Id: Ines's letters <letters.example.org>). Of a List-Id only the dot-atom inside its angle brackets (or a bare one) is kept, never its phrase, and one that is a link, a mailto or an address keeps no id and is counted. The unsubscribe links and mailto addresses are never kept, not even in part: they carry a token that says who you are. Header names are read in any case. A list header whose value does not parse is kept by its name ({"unsubscribe": true} for a List-Unsubscribe with no <link>) and counted (list headers that would not parse).

    Nothing already in the record is rewritten, and re-adding an export or syncing again appends nothing for a message the record holds (ADR 0017), so lines written before that day simply have neither key: absent means not said, never "not a list" or "Primary". lab hold census senders counts both (Hold).

    The people on a message are never resolved here. Every sender and recipient stays in the line as {email, name}, the same ref a resolution/v1 line names (RFC 0006), so one resolution of an address covers the calendar, the transcripts and the mail; the names a mailbox uses for an address are the candidates people merge proposes from. The adapter writes no resolution line of its own.

    Built for a 20 GB export

    The file is read in 8 MB chunks and scanned for separator lines; one message is in memory at a time, whatever its size (with the record to ask, what was read of up to 200 messages, 32 MB at most, waits for its answer). Headers are parsed by hand, the MIME tree is walked by byte offsets, and an attachment is never decoded or copied: its length is counted from the base64 text (exact for base64 and unencoded parts). Only with --attachments is a part decoded, hashed and put in the store. On a laptop this reads well over 40 MB/s, so an export of twenty gigabytes is read in under ten minutes; the record's own writing (append_many, a checkpoint every 10,000 lines) is the rest of the time. Every 10,000 messages a line on stderr says how many were read, how many megabytes, and the rate:

      10,000 messages · 412 MB read · 71.3 MB/s

    Resuming. The inbox manifest, inbox/manifest.json beside the record, keeps a cursor per file and per set of options: the byte offset of the last message the record holds, written after every checkpoint. An import that stops — Ctrl-C, a crash, a full disk — picks up there the next time add mail runs on the same file with the same options (All mail.mbox: resuming at 8,421,113,344 of 21,474,836,480 bytes); a finished one reads nothing (read to the end already). The cursor is honoured only while the file is the same one (the digest of its first 4 KB and its size are checked); a new export, or --restart, reads from the first byte, and an import with other labels, --since or --account is another import with a cursor of its own. The record never depends on the manifest: re-adding an export appends nothing either way (ADR 0017); the cursor only saves the hours of reading. A dry run never writes it.

    The benchmark. tests/test_mail_scale.py generates a 500 MB synthetic mbox — fictional senders at example.org, six short plain-text messages in ten, three HTML newsletters, one with base64 attachments of 20 KB to 1.5 MB, with threads, folded headers, quoted-printable and mboxrd escapes — and asserts at least 40 MB/s and a flat peak RSS (under 200 MB for the 500 MB file), in a process of its own. It is slow: LOGBOOK_SLOW=1 uv run pytest tests/test_mail_scale.py. The quick tests in the same file check every message the standard library's mailbox finds is a line here, on a file read in 4 KB chunks so separators fall across chunk boundaries.

    Mail (IMAP)

    logbook sync mail reads the same mailbox live, over IMAP, so the record keeps up after the Takeout import without another export: mail is the last daily source to get a live feed, and promises reads it — the Sent mail most of all, which is where your own commitments are. IMAP is a standard: Gmail is the first server, not the only one. The configuration is the environment and nothing else:

    Variable What it is
    LOGBOOK_IMAP_HOST the server, imap.gmail.com for Gmail
    LOGBOOK_IMAP_USER the mailbox address; it is the account on every line and the prefix of its raw_id, so add mail --account <the same address> and the live pull dedupe each other
    LOGBOOK_IMAP_PASSWORD an app password. Never logged, never echoed, never written to any file by the command: it lives only in the environment of the user who runs the schedule (~/.config/logbook/sync.env, mode 600, which you write)
    LOGBOOK_IMAP_PORT optional, 993. TLS from the first byte, the certificate and the host name verified; never STARTTLS, never plaintext
    LOGBOOK_IMAP_FOLDERS optional, comma-separated. Without it: the folder the server flags \All — Gmail's [Gmail]/All Mail, found through LIST with SPECIAL-USE or the older XLIST — else INBOX and the folder flagged \Sent

    Gmail takes an app password only with 2-step verification on the account (Google Account → Security → 2-Step Verification → App passwords); the password is sixteen letters and is the only secret the source holds.

    logbook sync mail                                 # what is new in each folder since the last run
logbook sync mail --since 2026-03-01T00:00:00Z    # SEARCH SINCE that day instead (the record refuses the overlap)
logbook sync mail --dry-run                       # fetch the headers, count, write nothing
logbook sync mail --restart                       # every folder from its first message again

    Read-only, enforced. A folder is opened with EXAMINE, never SELECT; bodies are fetched with BODY.PEEK[], which marks nothing read; STORE, COPY, MOVE, EXPUNGE, APPEND and every flag change are absent from the source, and the tests assert on a fake server's command log that none was ever sent.

    One parser. Every message goes through the mbox adapter's own parse_message, with the server's INTERNALDATE standing where the mbox separator's date would (counted date_from_internaldate): the same fields, the same body cap, the same raw_id. Attachments are named, sized and digested (sha256; the bytes are in hand) and never stored.

    Labels are a snapshot. With Gmail's extension (X-GM-EXT-1) the labels and the thread id are fetched with the message and written where the Takeout import puts X-Gmail-Labels and X-GM-THRID — labels, spelled as Takeout spells them (Inbox, Sent), and extra.gmail_thread_id — as they stood at ingest, once; the source never revisits a message to update them. On a server without the extension the line carries neither. X-GM-LABELS does not carry Gmail's tabs, so a line from sync mail has no extra.gmail_category, with the extension or without; the list headers (extra.list) are read from the message as on every road.

    The watermark is for economy, the record's refusal is the guarantee. Per folder the source keeps {uidvalidity, uid} — the folder's UIDVALIDITY and the highest UID handled — under resume in state/mail.json, written only once the lines up to it are in the record. A connection lost midway leaves the mark at the last batch written and the next run resumes there; a folder whose UIDVALIDITY changed is read from its first message again, which costs headers and writes nothing new; a walk after a lost mark writes nothing new either, because the dedupe on (source, raw_id) refuses what the record holds. A first run by hand reads every folder from its first message; the first scheduled run reads the last 14 days (the schedule) as --since does, SINCE that day, and a folder with no message from that day on is marked at its last message, so the next run reads only what arrives after it.

    Headers first. Each batch of 200 UIDs is fetched as Message-ID and size alone, the record is asked which of those it holds (one SELECT), and only the other bodies are fetched, in batches of at most 32 MB by the sizes reported. The first run over a 400,000-message All Mail after the Takeout import fetches no body the record would refuse. The progress line per batch says what is true — [Gmail]/All Mail: 1,200 fetched, 37 new, 1,163 already in the record — never a guessed total, and the summary names each folder's mark.

    Errors are one sentence, never a value. The login refused names LOGBOOK_IMAP_USER and LOGBOOK_IMAP_PASSWORD; TLS failed names LOGBOOK_IMAP_HOST; a folder not on the server names the folder and LOGBOOK_IMAP_FOLDERS. doctor shows sync:mail configured or unconfigured by the variables' names alone, and sync --all runs mail among the quick sources, so the four runs of the schedule pick it up with no further configuration.

    Gmail over the API

    logbook sync gmail reads a Gmail mailbox over the Gmail API, read-only (gmail.readonly), with the Google Workspace service account every Google source shares: the two variables LOGBOOK_DRIVE_SA_KEY and LOGBOOK_DRIVE_USER, set up once as the tour's Google, on one key says, with the Gmail scope among those delegated. No password and no app password; each run mints an hour's token and keeps it in memory, and nothing it can store goes stale.

    logbook sync gmail --dry-run                        # list and read, count, write nothing
logbook sync gmail --since 2026-03-01T00:00:00Z     # what Gmail received from then on, for this run
logbook sync gmail                                  # what is new since the last run
logbook sync gmail --restart                        # every message again (the record refuses the overlap)

    The same line as IMAP. Each message is fetched whole, the bytes the mailbox stores, and goes through the same parse_message the Takeout import and sync mail use: the same fields, the same 64 KB body cap, the same raw_id, <account>:<Message-ID>, with LOGBOOK_DRIVE_USER as the account. So a mailbox synced over IMAP yesterday and over the API today is written once, and a Takeout imported with --account <the same address> dedupes against both. Gmail's internal date stands where IMAP's INTERNALDATE would, for a message whose Date header is missing. Attachments are named, sized and digested and never stored.

    Labels in the profile's slot. labels is spelled as IMAP's X-GM-LABELS gives it: Inbox, Sent, Important, Starred and your own labels by name (Boat/Engine for a nested one); the thread id is extra.gmail_thread_id, in decimal as IMAP and Takeout write it. Dropped from labels, because IMAP never shows them: UNREAD (a flag, not a label) and the category tabs (CATEGORY_UPDATES, CATEGORY_PROMOTIONS, …). The tab is kept instead as extra.gmail_category (updates, promotions, …; above), the one field in which this line differs from the one sync mail writes. Labels and the tab are a snapshot at ingest, as over IMAP.

    Not a line. A draft (neither sent nor received; its Message-ID is often the one the sent message will carry, which would then be refused), a message in Spam or Trash, and one deleted between being listed and being read: each is counted.

    Headers first, history next. Each page of message ids is read as metadata (the Message-ID header alone), the record is asked which it holds, and only the other bodies are fetched: after a Takeout import or an IMAP sync, the first run costs one small request per message and no body. The state in state/gmail.json is Gmail's history id, taken before anything is listed, and the newest internal date handled, written once the lines are in the record. A run reads the history since the id and lists nothing; when Gmail no longer keeps that history (about a week) the run says so and lists what Gmail received from a day before the newest message. The first run by hand lists every message; --since gives a shorter one, which then leaves a mark (its time as the newest date when nothing came after it, so a later list by date never reaches back past it), and on a later run lists from that time for that run alone, the mark left as it was. The first scheduled run is such a shorter one, the last 14 days (the schedule). A dry run stops at the first rate limit or quota answer instead of waiting. Rate limits and server errors are retried with a doubling wait; anything else stops the run on one line, exit 1, the mark where it was.

    IMAP or the API

    • A mailbox that is not Google's — Fastmail, iCloud, a provider's own, your own server: sync mail, IMAP. It is the standard every server speaks.
    • A Gmail address on your own Google Workspace, where you can create a service account and delegate to it: sync gmail. No app password (which needs 2-step verification and can be revoked from the account page), one key for mail, calendars, Drive and tasks, Gmail's history in place of a per-folder mark, and drafts, Spam and Trash left out.
    • A personal @gmail.com account has no Workspace to delegate from: sync mail with an app password.
    • Both, for one mailbox, is harmless: the lines are the same but for the tab, and sync --all runs mail before gmail, so whichever reads a message first writes it and the other is refused it. To keep one, unset the LOGBOOK_IMAP_* variables, or switch gmail off in policy/import.json (its key stays for the other Google sources).

    One email, one line

    The same message can reach the record by all three roads: the Takeout export, sync mail and sync gmail. They write the same line, but its key differs when the mailbox is named differently: an export added without --account keys its lines <Message-ID>, the live roads <account>:<Message-ID>, and the store refuses only the very same key. So every road, before it writes, asks the record whether it holds the message by its normalised Message-ID (message_id above), from any road, and skips and counts it when it does. Nothing written is touched; a message the record does not hold is written as before.

    • The mailbox decides. A line of the same mailbox (account), or one written without a mailbox (an export added without --account), holds the message. A line of another of your mailboxes does not: a message you received in two mailboxes is two lines, each with its own labels (RFC 0015, rule 1). An export added without --account names no mailbox, so a line of any of yours holds its message.
    • Spelled the same, or not. The record is asked by the keys a line of the message can carry (the id as the header spells it and normalised, under the road's account and bare; for an export without --account, under each of your owner_emails too): one query per batch of headers, before sync mail and sync gmail fetch a body, so a message the record holds under one of those keys costs a header and nothing more. A message read and still not found (the export asks once per 200 messages, the live roads again for the bodies they read) is then looked for among the mail lines of its days, by normalised Message-ID: a spelling no key guessed (<Berth.9@Mail.Example.ORG> in the export, Berth.9@MAIL.EXAMPLE.ORG on the server) is the same message, found at the cost of its body. Each day is read once per run, in whatever order the messages come. Two ids that differ before the @, even only in case, are two messages.
    • No Message-ID, no shared key. A message without one is keyed by the digest of its own bytes, and each road dedupes itself, as before: the Takeout export adds two headers of its own, so its bytes are not the server's and the two roads write a line each. An id without an @ (unknown, (none)) is no Message-ID either: a mailer that writes one writes it on every message, so it is never a key across roads, though each road's own key still dedupes it. Message-ID: <> names no message and is keyed by its bytes; before this, every such message of an export shared the key <> and was one line, so re-adding an export added before writes each of them, the first a second copy of what that line holds.
    • Said, dry run included. Each holder has a line of its own after the counts:
    gmail: 0 new lines of 0 seen from the beginning; marks in state/gmail.json
  history id 48213, newest message 2026-03-04T10:15:00Z
  3,412 already in the record from mail (an import without --account)

    or from mail (you@example.org) for a line of that mailbox. --dry-run says the same and writes nothing. - A record that seals. Mail is tier 2: in a record that seals (RFC 0029) its lines are sealed and the index holds their keys blinded. With your identity here both questions are answered as above. Without it nothing can be read by Message-ID: a dry run counts every message as new, and a run is refused by the record, which writes no sealed line without the identity.

    Adding a Takeout export with --account <the address> still helps: its lines then name the mailbox, so a second mailbox's copy of the same message stays its own.

    What is counted, never dropped silently

    add reports: messages without a Message-ID (keyed by digest), timed by the mbox separator (no Date), with the body taken from HTML, with the body cut at 64 KB, with undecodable bytes replaced, attachments referenced or stored, messages skipped by label, and list headers that would not parse (each still kept by its name under extra.list). A message with neither a readable Date nor a readable separator is the only one skipped (skipped_no_date).

    add mail, sync mail and sync gmail report messages already in the record from another road or under another key, one line per mailbox (One email, one line). sync mail reports, besides these: messages already in the record by Message-ID, whose bodies were never fetched, and folders read from the first message again because their UIDVALIDITY changed. sync gmail reports messages already in the record by Message-ID, whose bodies were never fetched, drafts, messages in Spam or Trash, and messages deleted before they could be read.

    show prints ✉ subject — from → to (n attachments), never the body; show --raw prints the body under the row.
