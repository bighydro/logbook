# Changelog

## Unreleased

### Added
- A stay aboard an asset is a container (`stays.fold`, `Segment.inside`): the run of the owner's stays and moves aboard one asset is one stay `aboard <asset>`, from the first's start to the last's end, with the run inside it, so the asset's movement never fragments the owner's stay. Boarding takes twenty minutes: the asset's own location lines within the stay radius of the owner's points for `aboard_min_s` (1200 s by default, a new key of `policy/stays.json`) or longer; a boat that passes the quay once no longer boards the owner. Under way the asset's position at an owner's instant is read between its two fixes around it when they are at most twice `aboard_window_s` apart, so an AIS fix every ten minutes still places a passage. The overnight rule counts the stay aboard whole — a passage through the night is a night aboard, never in transit — and the night names the asset and carries the asset's position, the inner stay that held the longest part of the night (`Night.inside`, `Night.position`). `derive stays` prints the container with its run indented and the night with the asset's position (`--json`: `inside` on the stay; `aboard`, `inside` and `position` on every night); `day` builds its `aboard` row from it, shows the position in the header (`night after   aboard REDUCE · 59.3400,10.5500 · away`) and reads the country from it; `trips` makes a night aboard a route element `aboard <asset>` (the asset's name) and counts the trip's nights aboard per asset (`nights_aboard`; the text says `5 nights (2 aboard Solvind)` on a mixed trip); `rollup places` gains an **aboard** section, one stay per run aboard with the run's whole hours (the JSON key `assets` is now `aboard`), while the anchorages inside it remain unnamed places marked `aboard`, and a night aboard counts at the anchorage the asset lay at; `rollup people` and `rollup countries` read the night there too. Synthetic fixture: the yacht REDUCE (MMSI 970123456, which does not exist) motoring 40 km through a night with the persona aboard, and the control case with the persona ashore at a cabin 3 km away ([docs/day.md](docs/day.md), *Aboard an asset*).

### Fixed
- `promises`, who said it: a line of a note, or of a turn a diarizer gave the owner, that begins `Speaker 2:` (or with the name of a participant, of a person the record resolves, or of the owner) belongs to that speaker, never to the owner; the owner is `you` only when the label resolves to one of their identities (`promises.relabel`). Before, every note was the owner's whole, and a mixed turn kept the source's label. A word before a colon that names nobody (`Plan:`) stays text.
- Every reader piped into `head`, or into a consumer that quit already: quiet, status 0. The CLI caught a pipe that broke on a write in the middle of a long listing; a short one — a fortnight of `days`, one `day`, `stats` — sat in the buffer until the interpreter's final flush and reported `Exception ignored in: <_io.TextIOWrapper name='<stdout>'> BrokenPipeError` with status 120. `main` now flushes before it returns, and before a command's own exit status (`sources --gaps` exits 1) is passed on, so the pipe is met there and stdout turned to the null device (`tests/test_broken_pipe.py`, every reader).
- `days` and `day`, the night: a night whose stay centre is within 400 m of a place of kind `home` (`stays.HOME_NEAR_M`, the night rule `trips` already followed) names that place — `Home` — where the row printed the coordinates of a stay at home; an unnamed stay within 5 km of a named place reads `59.9200,10.7400 near Home, 1.0 km`, the route's rule (`trips.coordinates_label`, now shared by `trips` and the Day; the Day printed the bare coordinates); and `days` prints `no location` instead of `in transit` when the day has no location line at all (`night.located` under `--json`), since nothing then says the owner moved — `in transit` is for a day on the road with no stay reaching the minimum.
- `rollup health`, `stats --health` and the Day's health line: HRV is reported in ms, always. `health.ms` reads a line as stored — a value in `s` is multiplied by 1,000, one in `ms` is taken as it is — as `health.bpm` already read a resting rate in count/s; a single 45 ms sample is `hrv 45 ms (1 day)`. `repair health-units` stamps every corrected line with the profile's unit (`repair.HEALTH_UNITS`: `bpm`, `ms`). The Apple Health adapter already wrote HRV SDNN (type 183) in ms unscaled; a test now holds it to that.
- `trips` and `day`, a stay at an airport: labelled by the airport's IATA code and city — `ZRH, Zurich` (`trips.airport_label`; the code alone when the row names no municipality) — where the route printed the row's name and the Day the bare coordinates. An airport with scheduled traffic (the airports table's new `type` column, OurAirports' own: `large_airport`, `medium_airport`; `Airport.scheduled`) holds a stay within 3.5 km of its reference point (`trips.SCHEDULED_AIRPORT_KM`), since the row marks the runway midpoint and a terminal often lies 2–3 km off it, so a stop at a large airport read as coordinates with the city in parentheses; every other row keeps 2 km (`trips.airport_at` is the rule, `Airports.within` the lookup). Every built-in row is `large_airport`, as the generator's filter has always kept; `scripts/make_airports.py` writes the column; an override file may carry it or leave it out. Tested on a synthetic field whose terminal is 2.8 km from the reference point.
- `show`, three places the reference did not read the record as SPEC §3.2 says, found by logbook-ts diffing the conformance sample against it (its SPEC-QUESTIONS 24, 25, 27 and 40): a collapsed run of location points now ends at the last point's `end` when it has one, else at its `at` (it ended at the `at` regardless; one point is still a row of its own and prints its `at`); a payload without a renderer, the `key=value` row, spells a number as RFC 8785 writes it, by value and never by the text the writer stored — `100000000000000000000`, not `1e+20`; `0.000001`, not `1e-06`; `120`, not `120.0` (`chain.number_text`, the serialiser the chain already uses) — while a nested object, list, string, boolean and null keep Python's spelling; and a `message/v1` line whose `chat` is a string, the shape before RFC 0008 that the conformance sample carries, reads as a direct chat of that name instead of raising, and a `chat` of any other non-object shape is read as no chat. Every day of `conformance/sample-logbook` now prints, and 2026-03-01 and 2026-03-06 are pinned whole in `tests/test_show.py` as the cross-implementation fixture; `expected.json` is unchanged, since it carries `seq` and `head` only.
- `day`, `trips`, the pages and `rollup people`, "with" from a note: a name a note says `with` counts only when the record resolves it to a person, the rule transcripts already follow (`present.from_notes`); `with US`, `with XYZ`, a country, an acronym or a name no resolution line knows names nobody, where before it was kept as written. (A real record listed `US` as company.)
- `show` and `day`: one calendar entry several sources carry — two or more `event/v1` lines from different sources (`ics`, `ios-calendar`, `gcal`) with the same start and end, naming the same flight in the title or carrying the same title, case, accents and whitespace aside — is one row, `×N sources` (`logbook/events.py`, `fold`): the same flight in four calendars in two languages reads once, `×4 sources`. `show` folded within five minutes before and printed `ics+ios-calendar`; it now folds on the exact times, as `day` does. Under `--json` the Day's event carries `sources` and every `lines` it stands for; the sources line still counts every calendar's lines.
- `day`: a stop with nothing attached reads `nothing attached` after its place and duration; the kind column already says stop, so the row never read `stop · stop`.
- `trips` and `day`, an unnamed stay: when it is at no large airport (2 km) and near no named place (5 km), the coordinates carry the city of the nearest large airport within 30 km in parentheses — `53.5998,10.0130 (Hamburg)`, the city only, never the airport's name — so a reader sees where a hotel is. The city is the airports table's new `municipality` column (OurAirports' own text, `Oslo (Gardermoen)`; `Airport.city` keeps the part before a parenthesis or a comma; `scripts/make_airports.py` writes it, and the table is regenerated with no other row changed). The airport-name helper #132 left unused is gone with its test.
- `flight/v1` (RFC 0013 rule 1): a codeshare pair — two lines on one date and route whose departures are within 30 minutes, the operating carrier's number and a marketing carrier's (XY 123 and XY 9123) — is one flight: `reconcile` merges the second into the first under merge-and-supersede, keeping the operating carrier's designator when a producer marked it (`extra.operating` true), else the one first seen; `standing` folds a pair the record already holds unmerged the same way, so `rollup flights` and `trips` show it once (`in XY 561 OSL → ZRH`, not twice). Before, only identical numbers merged.
- `infer flights` never copies a flight number onto a leg that is not the flight the calendar entry names: when a tracked or declared flight in the entry's window already holds the entry's designator on another route, the leg is written with neither `carrier` nor `number`, keyed by date and route (`(date, "", "ZRH>IST")`); `show`, `rollup` and `trips` print such a line as its route alone. Before, a two-day entry naming the tracked outbound put that number on the next day's onward leg.
- `infer flights` emits nothing for a leg between airports under 150 km apart (`MIN_KM`): the points left one airport and reached the other, but it was a drive.
- `infer flights` emits nothing for a leg a tracked flight on the same route already covers under another key — a flight landing after local midnight, a stale point at the origin after departure — counted as `covered` ("legs a tracked flight already covers"). The same key still merges into the tracked flight as before.
### Readers
- `logbook promises --judge [--limit N] [--model NAME] [--fetch-model]` (`logbook/judge.py`, `docs/promises.md`): a local instruct model reads each candidate the rules found — the sentence marked among the two sentences either side of it in the same transcript or note, across turns, each with who said it; the day, the title, the owner's name and the names the record resolves in that line — and answers one JSON verdict at temperature 0: `is_commitment`, `by` (`owner`, a name, `unknown`), `to`, `what` (the speaker's words shortened), `due` (`YYYY-MM-DD` or null) and `confidence` (0 to 1). The engine is `mlx-lm` on Apple silicon, the new optional extra `openlogbook[judge]`, with `mlx-community/Qwen2.5-7B-Instruct-4bit` by default and `--model` for any MLX instruct model; it is imported only when `--judge` runs, the hub is offline while it runs (no socket is opened, as `transcribe` has it), a model not on the machine stops the command naming `--fetch-model`, and without the extra `--judge` stops with the message that names it. Never a cloud model. The verdicts are kept in `policy/promises-cache.json` by candidate id with the engine and model that gave them, rewritten after each one, so an interrupted run keeps what it did and a candidate is never judged twice; an answer with no whole verdict is counted and tried again next run. `logbook promises` now shows the judged commitments at confidence 0.6 or above (`promises.THRESHOLD`) and says how many candidates are unjudged; `--all` shows every candidate; a judged row carries the confidence, `to <name>` and, for a non-commitment, `no`; under `--json` every proposal carries its `judgement` or null, and the report `judged_only`, `threshold`, `judge` and `unjudged`. `promises done <id>` is unchanged and the only write to the chain. Each proposal carries the context the judge sees (`Proposal.before`, `.after`, `.names`). Tested through a fake engine: the prompt's attribution and context window, the cache, the threshold, the limit, the no-socket guard and that nothing reaches the chain but through `done`.
- `logbook year YYYY [--html PATH] [--json]` (`logbook/year.py`, `docs/year.md`): one calendar year read back, composed from the readers that exist over one reading of the year's days (the days the owner's track covers, clipped as `rollup --year` clips): the days per country (`rollup countries`), the nights home, away, in transit and aboard each asset (`rollup nights`), the trips in order with their nights, route, flights in and out and companions (`trips`), the flights with their kilometres and evidence (`rollup flights`), the places by nights — named, assets, the top unnamed clusters — with the people confirmed there (`rollup places`), the people by days together (`rollup people`), the health lines by month (`rollup health --by month`), the keepers by month and lane (RFC 0024), and twelve picks, one day each: for every month the day with the most evidence — the attachments across the Day's rows plus the people confirmed plus one for a flight or a new place (a named place not stayed at earlier in the year, or an unnamed stay more than 300 m from every earlier one; home never) — of equals the day with more lines, then the earlier; a month with no line is `no days`. Each pick is read with the day reader (`day.read`, the night before in it) and printed as `logbook day` prints it; under `--json` the Days are inside and every day's evidence is under `scored`. `--html` writes one self-contained page — inline CSS, no script, no asset, nothing fetched, everything escaped — that prints with table headers on every sheet and no pick split; `--json` is one object with the chain head it was read at. Nothing is written. Tested on the 365-day demo record and the persona's fortnight (the month-pick rule, hand-checked).
- `places propose` reads the index, not the files (`reading.owner_track`): the owner's location points and the registered assets', the evidence that promotes a stay and the retracted ids are columns of `index.sqlite` now (`subject`, `lat`, `lon`, `end`; schema 5, so an older index is rebuilt once on the first reader), `--since`/`--until` are cut in the query, and the clustering runs from the rows — no month file is opened, however long the window, and the cost is linear in the points of the window (half a million lines over two years in four seconds, 2.8 million points in the window in under half a minute, on a small cloud box) where before every line of the window was parsed from the files. The only lines read whole are the Google Timeline visits, found through the index by their `raw_id`. Same output as before, pinned on the demo record (`tests/fixtures/demo/places_propose.*`); a generated two-year record of half a million lines asserts not one file is opened (`LOGBOOK_SLOW=1`). Along the way `derive stays` attaches evidence and matches an asset's track by binary search instead of a pass over the window per cluster, so a long window no longer grows quadratically; a stay aboard an asset is unchanged. The points `propose` clusters are the owner's and those of the assets `assets.json` names: a subject the registry does not name is not read, since nothing of the owner's can be aboard it.
- `logbook days [--from YYYY-MM-DD] [--to YYYY-MM-DD] [--json]` (`logbook/days.py`, `docs/day.md`): a window of the record read back one line per day, composed from the Day of each (`day.of_reading`, the Day built from a reading the caller holds; `day.health_rows`, `day.counts`, `day.health_text` and `day.distance_text` exposed for it, the Day's own output unchanged). Each line: the date and weekday; where the night was spent (the night after: a named place, `aboard <asset>` or the coordinates with the nearest large airport's city, and the country when the night is away; `in transit`); the kilometres moved (every move that started on the day, the flights' included; aboard an asset, its passages); the flights (`XY 561 OSL→ZRH`); the stays (a stay or a run aboard an asset) with how many lines are attached across the day's rows; the people confirmed present; the health triple when the day has one; and a gap marker naming every usual source with no standing line that day — usual: with a line on at least four in five of the window's logged days, counted on the index in one aggregate (`Index.source_days`, new), so a tracker that fell silent is seen and a calendar that spoke once is not missed daily. The window is read in chunks of a month through one `reading.read` each (the chunk's days and the day before; the chunk's health lines in one indexed query), so a year is a dozen readings, never one per day, and the lines stream out as each chunk is read: a year of the demo record prints in seconds, the first line within one. Both bounds default to the days the owner's track covers. `--json` is JSON Lines, one object per day. Nothing is written.
- `logbook rollup health [--year YYYY | --since YYYY-MM-DD --until YYYY-MM-DD] [--by month|week] [--json]` (`logbook/rollup.py`, `docs/rollups.md`): the `health-sample/v1` lines (RFC 0014) summed up per calendar month, or per ISO week (`2026-W23`) with `--by week` — sleep (the mean of the nights' hours and how many nights had a line; a night the asleep stages of the night that ends on the day, per device the union of their spans, the longest device, rules 4 and 5), steps (the mean of the days' counts and how many days; a day the larger device per quarter hour, summed), resting heart rate (the mean, lowest and highest of the days' rates in bpm, and how many days) and HRV when the record has any (the mean of the days' SDNN in ms, and how many days). A correction that `supersedes` a line wins, the latest when a line was corrected more than once; a retracted line is out. Units as stored: a resting rate in `count/s` is read in bpm (×60), one in `bpm` or `count/min` as it is. Every month or week the window touches is a row, and a field no day of the period has a line for prints an em dash and is `null` under `--json`, never a zero. The window is clipped to the first and last day with a health line and read through the index alone, with no reading of the track. Under `--json` every number carries the ids of the lines it came from. `--by` is refused for any other kind. `docs/rollups.md` is new: every rollup in one page.
- `logbook/health.py` (`stats --health`, the Day's health line, `rollup health`): the day rows carry `hrv`, the mean of the day's heart-rate variability readings in whole ms (`stats --health --json` and the Day's JSON gain the field; the tables are unchanged); a resting reading is read in the unit its line states (`count/s` ×60 to bpm), where before the value was taken as bpm whatever the unit; of several lines that supersede the same line the latest stands and the earlier corrections are out with it, where before every correction stood.
- `logbook rollup places [--year YYYY] [--with]` (`docs/rollups.md`): every named place and asset now carries its **nights** — the days whose overnight stay is there — beside its stays, hours, first and last visit and company; and each year lists the top five **unnamed** clusters, the owner's stays at no named place grouped as `places propose` groups them (300 m) and ranked by hours, each under the stay id `places name` takes, with its label (the coordinates; `aboard <asset>`; `near <place>, x km` within 5 km; else the city of the nearest large airport, the `trips` rule), its nearest named place, nights, stays, hours and company. Each person at a place carries their `stays`, `days` and `nights` there; a night counts for a person when the evidence that put them at the stay is dated the night's day, so dinner on the 16th is that night together, not every night of the stay. `--with` is the place × person table — one row per person per place, stays, days and nights — printed as a table and, under `--json`, as `with` per year; it goes with `places` only.
- `logbook rollup people [--year YYYY]`: the confirmed set of the with module only. A tagged face and an all-day entry's attendee are proposals and no longer a listed person, a counted line or a `proposed` number: a person the record knows only by a face is not in the rollup (the Day and the pages still propose them); the owner is never listed. Each person gains `nights` together (the `--with` rule) and `stays` shared; an unnamed shared place reads with its city or its nearest named place instead of bare coordinates. `unresolved` keeps the confirmed names the record resolves to no person.
- `present.Evidence`: the window's evidence lines (events, transcripts, notes, photos) bucketed by every local day their span touches, so the company of a stay is one lookup over the lines of its days and never a pass over the whole window per stay or per place; `rollup places` and `rollup people` read through it, from one reading of the window through the index and one derivation of the stays.
- `logbook day YYYY-MM-DD [--json]` (`logbook/day.py`, `docs/day.md`): one calendar day read back. The header — the date, the night before and the night after (a named place, `aboard <asset>` or the coordinates; home, away or in transit), the country of the day from the night's stay by the `rollup countries` rule (else the longest stay of the day), the day's all-day entries. The timeline — the owner's stays, stops and moves from `derive stays` that touch the day, clipped to it for display and keeping their real span, and the flights of the day from the `flight/v1` lines standing (`flights.standing`, the merged set) as rows of their own with their evidence (`tracked`, `inferred`, `declared`); a run of segments aboard one asset is one stay `aboard <asset>` with the berth, the passage and the anchorage inside it, so the asset's movement never fragments the stay; a move with no points that lasts a silence or more and is not a flight is a `gap`, said so, and places nothing. Under each row its attachments, named for events, transcripts, notes, mail threads, calls and keepers and counted for messages and photos, and `with`, the people there split into confirmed (a note's declaration, a transcript's speaker, a timed calendar entry's attendee) and proposed (a face, an all-day entry's attendee), never the owner; a move carries attachments but no company. Then the lines inside no row (`unplaced`: the calendar's plan where the track has nothing), the health line (sleep hours, steps, resting heart rate) and the sources with their newest line's time, so a tracker's silence is seen. Read through the index from one `reading.read` of the day and the day before; nothing is written, not even `policy/stays.json`. Under `--json` every row carries the ids of its lines.
- `present` (the with module): an all-day calendar entry's attendees are proposed (confidence 0.3), never confirmed — the entry names no hour; and only when the entry is located at the stay (its coordinates or a named place within 1 km), since an all-day entry with no location overlaps every stay of its day and places nobody at any one of them; `present` and `company` take `owner` (`present.Owner`, built by `owner_of` from `owner_id` and `owner_emails` in `logbook.json`, `policy/owner.json` and the resolution lines) and never list the owner as company.
- `logbook/health.py`: the `stats --health` summary (sleep, steps, resting heart rate per day, RFC 0014 rules 4 and 5) moved out of the CLI so the Day shares it; a health line another health line `supersedes` (a `repair health-units` correction) is out and the correction stands, as a retracted line already was; each row carries the ids of the lines its numbers came from (`stats` drops them).
### Commands
- `logbook sync --all`: every configured live source in turn — configured: at least one of its `ENV` variables set and its `configure` taking the environment — each from its own watermark, a source the owner disabled (`policy/import.json`) or one with no variable set skipped and said so; a failure in one (its exit status, or an error its adapter let through) is said on stderr and never stops the next. Each source prints its summary as it runs; then one line per source (`ok`, `failed (status 1)`, `skipped (LOGBOOK_GRANOLA_KEY not set)`) and exit 1 when any failed. A Ctrl-C while a source listens to a stream (`ais`, status 130) ends the run there, the sources not reached listed as `not run`, status 130. `--dry-run` passes through; `--since`, `--listen` and `--until` are a single source's and refused with `--all`. `logbook sync --install-schedule` / `--uninstall-schedule` (`logbook/schedule.py`, README): `sync --all` at 07:00 and 19:00 local by the machine's own scheduler — a launchd agent on macOS (`~/Library/LaunchAgents/org.logbook.sync.plist`, `StartCalendarInterval`), a systemd user timer on Linux (`~/.config/systemd/user/logbook-sync.{service,timer}`, `$XDG_CONFIG_HOME` honoured, `OnCalendar=*-*-* 07,19:00:00`, `Persistent=true`). The plist or units are printed before they are written; nothing is written outside that one directory; the agent runs the interpreter that installed it (`sys.executable -m logbook.cli`) and carries `LOGBOOK_HOME` for the record found at install time; a live source's keys are never written — both read `~/.config/logbook/sync.env` (`KEY=value`, the owner's file) at run time, so the schedule is harmless until the file exists. The scheduler is then told (`launchctl bootstrap`, `systemctl --user enable --now`); when it is not on PATH the command to run is printed; a scheduler that refuses is exit 1 with its words, the files left for a retry. Any other platform exits 2.
- `logbook digest [YYYY-MM-DD] [--json | --markdown]` (`logbook/digest.py`, `docs/digest.md`): the day in 25 lines at most, what the owner reads of it in the evening, composed from the readers and deriving nothing of its own. The Day's shape in three lines — **where** (the stays in order, a run aboard an asset as `aboard <asset>`, and the night after: at home, away or in transit), **with** (the people the Day confirms, and how many are only proposed), **attached** (the counts across the day's rows, and how many lines fell inside no row); the flights of the day, three at most and `+N more`; the open promises due on the day or within seven days after it from the promises reader (`promises.extract`; a report that carries a `judged` set, the ids a judging reader holds to be promises, is narrowed to those — `digest.due_promises`), three at most; the usual sources with no line on the day by the `sources --gaps` rule (`gaps.report` with the day as `since` and the usual sources of the fortnight expected, `days.usual_sources`), one line; tomorrow's timed calendar entries from the `event/v1` lines standing, folded as the Day folds them, with the attendees the record names, three at most; and, last, one closing question the owner can answer in a word, by the first rule that applies — a day with no line asks whether the missing usual source was switched off, else where you were; a night in transit where you slept; a person proposed and confirmed nowhere whether they were with you; a calendar entry inside no row whether it happened; a missing usual source whether it was off; a promise due by the day whether it is done; else `Anything to add?` — so the day closes itself (ADR 0005). The 25 lines are a hard limit (`digest.LIMIT`): the parts are capped and `digest.fit` cuts from the middle, never the header or the question; the JSON holds the whole sets and says how many lines the text has. `--markdown` prints the same lines as a heading, a bulleted list and the question in bold. Nothing is written, not even the settings file; nothing is sent — delivery is a later decision. A day after today in the record's zone is refused.
- `logbook people [--year YYYY] [--json]` and `logbook person <name-or-ref> [--year YYYY] [--json]` (`logbook/people.py`, `docs/people.md`): everyone the record's resolution lines name as a person (RFC 0006), never the owner, and what the record knows of each. Per person: the channels they come through, each with its lines, first and last day, highest tier and last line — `messages` (a `message/v1` they sent, and one the owner sent in a direct chat with them: attributed to the one person who wrote in that chat, else to the person the chat's id names, a WhatsApp JID being a phone number; the owner's lines in a group name nobody), `calls` (answered or not), `mail` (from them or to them, by address), `calendar` (an entry they attend and did not decline, timed or all-day), `transcripts` (a participant, by ref or by a spoken name the record labels one person by), `faces` (a tagged face, through the library's person id); first and last contact over every channel; the days together, the with module's confirmed set (the rules of `trips` and `rollup people`: a tagged face and an all-day entry are proposals, not a day together); the nights under one roof (the nights whose overnight stay the person was confirmed at on that day); the places shared, by days there, labelled as the rollups label a stay; the birthday when a standing resolution line of one of their refs carries `extra.birthday` (`YYYY-MM-DD` or `--MM-DD`); and the last real contact — the latest message, answered call or day together, with how (`message`, `call`, `meeting`); a mail is a channel and never a real contact, a newsletter being a mail too. The tier of a person is the highest tier of their evidence, the resolution lines included; the report's is the highest of its people. `people` is one row per person with evidence in the window, most days together first; `person` is one page — the same numbers, then the shared days, most recent first, each with where, the evidence and `night` when the night was spent under one roof — found by label, a unique first or last name, entity id, address, phone number or `kind:value`; several, nobody or the owner exit 2. The window is the record's days of any kind, or `--year` clipped to them. Read through the index and nothing else: the resolution and retraction lines whole, the owner's stays and nights from the index's columns (`reading.owner_track`), and the six kinds streamed one at a time over the window (`Index.of_kind` now takes local-day bounds), each line read once and kept only when it names someone; a retracted line and one another line of its kind supersedes count for nothing. Synthetic fixtures: the Oslo persona's circle of twelve (`tests/circle.py`).
- `logbook mcp [--root DIR] [--allow-tier-3]` and `logbook mcp --inspect` (`logbook/mcp_server.py`, the optional extra `openlogbook[mcp]`, `docs/mcp.md`): the record served to an MCP host on this machine over the process's own stdin and stdout, and nothing else — no TCP, no socket. Nine read tools answer as the commands' `--json` does — `day(date)`, `days(from, to)`, `trips(year)`, `places()`, `people()`, `person(name)`, `promises(open)`, `gaps(since)` — and `search(text, since, until, kinds, limit)` finds, through the index, the standing lines of a window of local days and a list of kinds whose payload mentions the text, case aside; two write tools go through `Logbook.append` and nothing else, `add_note(text, at?)` (one `note/v1` line, tier 2, as `logbook add`) and `promise_done(id)` (one `task/v1` line, as `logbook promises done`). Every tool's output passes the crossing gate of ADR 0016: `policy/crossing.json` names an `mcp` destination (`init` writes `{"max_tier": 1}`; a file that does not name it is a ceiling of 1, `policy.mcp_ceiling`, the one destination with a default), read on every call and never written; a line above the ceiling is left out of every reading before anything is derived from it (a `GatedIndex` filters every line, row and aggregate the index serves, so a tier-2 note is in no Day, page, rollup or search at max_tier 1), the answer carries `gate.withheld`, the count of lines left out, and a retraction passes whatever its tier so a retracted line stays hidden. Tier 3 crosses only when the policy allows it and the server was started with `--allow-tier-3`. A read appends no crossing line. `--inspect` prints the tool table and one sample request, with neither a record nor the extra. Tests drive the server through the SDK's in-process client over the synthetic persona; no socket opens.
- `logbook sources --gaps [--since YYYY-MM-DD] [--expect SOURCE...] [--json]` (`logbook/gaps.py`): where each source went quiet, from the index alone (`Index.activity`: three SELECTs over its columns, one a window query for the longest stretch between consecutive lines; nothing read from the files, however long the log). Per source with lines in the range: the lines, the last line's time, the longest silent stretch (between two lines, from the range's start to the first line under `--since`, or since the last line and still running, `since 2026-09-20 21:00`) and the local days with no line, folded into runs (`2026-09-21..2026-09-30`). The range is each source's first day to today in the record's zone, or `--since`; a line dated after today (a calendar's future entries) is outside it; today is a missing day only once the source has been silent a full day. `--expect` shows only the named sources, a source with no line among them (`no lines`), marks one silent a day or more at any point of the range with `!`, and exits 1 when any is marked, so a cron job can say so. Every line counts, retracted or not. `--since`, `--expect` or `--json` without `--gaps`, a malformed day or one after today exit 2. The plain `sources` listing is unchanged.
- `logbook assets status [--json]` (`logbook/asset_status.py`): per asset of `assets.json`, in registry order, its last known position and how old that fix is — the local time of the fix, `lat,lon` to four decimals, `near <place>, x m|km` for the nearest named place of `places.json` within 5 km (a berth, a harbour, the cabin's jetty), the speed in m/s when the line carries `speed_mps`, and `3 days 4 h ago`; `no fix yet` for an asset the record has never placed. The fix is the asset's standing `location/v1` line with the latest `at` whose `subject` is its id (RFC 0001, ADR 0018), the latest by time, not by order of writing; a retracted or superseded line never counts. Found through the index: `index.sqlite` gains a `subject` column and a `(subject, at)` index (schema 4; an index built by an earlier schema is rebuilt once, by the first reader, as before), so the lookup is one SELECT per asset and one line read from the files, whatever the size of the owner's own track. Under `--json` each asset carries its registry entry and `fix` (`at`, `lat`, `lon`, `speed_mps`, `near {name, m}`, `age_s`, `line`) or `null`. Nothing is written.
- `logbook doctor` (`logbook/doctor.py`): is this machine set up to keep the record? One line per check, `pass`, `warn` or `fail`, a summary, and exit 1 when anything fails; it reads and never writes, not even the empty settings file a reader would create. The checks: the record is found and `verify` is green with `logbook.json` at the head (not found, not intact or `logbook/0.1` is a fail naming what to run); `index.sqlite` is current, read through a read-only connection so a build in progress is never discarded (missing or behind is a warn); `policy/owner.json` is there and names at least one alias (missing or empty a warn, not JSON a fail); `places.json` names a place of kind `home` (none a warn, with the `places add` line); `assets.json` is a registry when it exists; each optional extra, `ais`, `encrypted` and `transcribe`, is installed, found without importing it, with `pip install "openlogbook[<extra>]"` when not; for every live source the record uses — a `state/<name>.json` watermark, or lines of that source when the index is current, never one `policy/import.json` disables — the variables its adapter reads are set, by name only and never a value, and one the adapter refuses says to run `logbook sync <name>` rather than echo it; free space on the record's volume (under 5 GiB a warn, under 512 MiB a fail); and the folder is not one a sync client owns — iCloud Drive (`iCloud Drive`, `Mobile Documents`, `com~apple~CloudDocs`), Dropbox, OneDrive (the folder name or Windows' `OneDrive` variable) or Google Drive — by any part of the path as given or resolved, a fail with the reason. README, "Where to keep the record".
- `logbook sync ais --listen SECONDS` and `--until HH:MM` (`logbook/adapters/ais.py`): one long sitting at the aisstream.io websocket instead of a 60 s window per cron run. `--listen` is the window in seconds, `--until` the record's local time the clock next shows (later today, else tomorrow; a window across the night the clocks change is the hours that pass); without either, `LOGBOOK_AISSTREAM_LISTEN_S` as before. While it listens: one line a minute on stderr with the messages heard, per asset (`8 reports in 120s (solvind 7)`), quiet socket or not; a socket that drops, or a reconnect that fails, is tried again after a wait that doubles from 1 s to 60 s and starts over once a connection delivers, the subscription sent anew each time (said on stderr, counted as `reconnected N times`); a refused key is never retried. Ctrl-C ends the listening, not the run: what was heard is written in time order, the summary printed, and the exit status is 130. The key comes from `LOGBOOK_AISSTREAM_KEY` only and is in no line, notice or error. The flags are refused for a source that does not listen, and `--listen` with `--until`.
- `logbook promises [--since YYYY-MM-DD] [--open] [--json]` and `logbook promises done <id> [--note TEXT]` (`logbook/promises.py`, `docs/promises.md`): the commitments the record's own words suggest, proposed and never asserted. One proposal per sentence of a standing `transcript/v1` or `note/v1` line (retracted and superseded lines left out) that carries a first-person future or obligation cue in English or German — `I'll`, `I will`, `I'm going to`, `we'll get back`, `I promise`, `I need to`, `I have to`, `I must`, `let me` (not `let me know`); `ich werde`, `ich schicke`, `ich melde mich`, `ich kümmere mich`, `ich rufe`, `ich muss`, `wir müssen` — not negated right after it (`I will not`, `ich werde nicht`) and not a question; by rules alone, no model, no network. Each carries the local day and time of its line, the origin line id, the speaker when the transcript resolves one (the turn's label matched to `participants`, their refs to a person through the resolution lines, RFC 0006; `me` and the owner's names are `you`, as is every note; `Speaker A` stays as spoken with no person), the sentence as written, and a due hint with a `?` when a date phrase is in it, resolved against the day it was said (a weekday is the next one strictly after; `next week` its Monday; `this week` and `end of the week` the Friday on or after; `tomorrow`, `morgen`, `tonight`, `in two weeks`, `next month`, `by June 20`, `bis 20. Juni`, `bis zum 20.6.`, `the 5th`). A transcript's text is read from the attachment store by media type (WebVTT, SRT, Granola's JSON segments, `Speaker: text` prose, plain text) through the file adapter's parsers; one whose text is not in the store is counted and skipped. The proposal id is a sixteen-hex digest of the origin line and the quoted sentence, so it is the same on every run and for any extractor that quotes the same sentence. `--json` is the report: `extractor`, `skipped`, and every proposal with `id`, `status`, `closed_by`, `day`, `at`, `line`, `seq`, `kind`, `source`, `title`, `speaker`, `direction` (`owed_by_owner`, `owed_to_owner`, null), `certainty` `inferred`, `language`, `cue`, `class`, `quote`, `due`. `done <id>` appends one `task/v1` line (RFC 0016): `source` `manual`, tier 2, the sentence as `title`, `status` `done`, the due hint as `due`, `completed_at`, `list` `promises`, the `--note` as `notes`, `raw_id` `promise:<id>@<time>`, and under `extra` the `promise` id, `origin`, `speaker` and `extractor`; `--open` hides a proposal whose latest standing task line is `done` or `cancelled`; a second `done` writes nothing and says so; an unknown id is refused. The extractor is a value — a `name`, a `version` and `__call__(text) -> list[Match]` — so a later local-model pass replaces the rules without changing the command, the report, the ids or `done`.
- `logbook transcribe voice-memos [--since YYYY-MM-DD] [--model NAME] [--dry-run] [--fetch-model]` (`logbook/transcribe.py`, `docs/adapters/voice-memos.md`): the local transcription step RFC 0023 leaves to later. One `transcript/v1` line (RFC 0004) per standing `voice-memo/v1` line whose audio is in the attachment store and that has no transcript yet, in time order, appended as each is heard, so an interrupted run keeps what it did and the next carries on. The line's `raw_id` is the memo's own, so a memo is transcribed once however often the command runs (ADR 0017); `source` is `transcription` whatever engine heard it; `provider` the engine; `payload.provenance` `{source, engine, model}` with `source` the memo line's id; `extra.recording` the memo's `raw_id`; `language` detected on the first chunk and asked of every later one; the text one segment per line as a `text/plain` attachment, never inline; `at`, `end`, `tz` and `title` the memo's; tier 2, or the memo's when higher. A retracted memo, and one another line supersedes, is left alone, and the transcript never carries `supersedes`. Long recordings are heard in ten-minute windows. Engines, as the optional extra `openlogbook[transcribe]`: `mlx-whisper` on Apple silicon, else `faster-whisper`, found at run time and imported only then; neither installed is one clear message. Nothing leaves the machine: the Hugging Face hub is told it is offline for the length of the run, so no socket is opened (a test refuses every socket while a fake engine hears a two-second synthetic WAV); a model not on this machine stops the command, and `--fetch-model` is the one explicit download. `--dry-run` lists and needs no engine. `--model` is a Whisper size (default `small`) or a repository.
- `logbook demo --days N --seed S --out DIR` (`logbook/demo.py`): a complete synthetic record to try every command on, invented in code and read from nowhere. The Oslo persona, Ines Nordmann, who does not exist, lives a four-week story that repeats for as many days as asked: an office week with a cabin weekend; Zürich for a client, out on a tracked flight (`flighty`, XY 561) and back on one the record infers from its own calendar entry and location points (`flight-inference`, XY 562, written as `logbook infer flights` would, so the command finds it already there and merges the other three); a week aboard the yacht Nordlys with the boat's own AIS track as a subject (`assets.json`, MMSI in the 970xxxxxx test range), so the nights read *aboard* and the trip is an asset trip; Copenhagen, out tracked (XY 571) and back declared (`manual`, XY 572). Around it every profile: location, event, message, transcript (the text in the attachment store), note, photo with favourites and an Art album (keepers follow), call, mail, task, browse, watch, listen, trip, highlight, voice-memo (a digest, no audio), health samples (sleep stages past midnight, steps in quarter hours, resting and ambient heart rate), transaction, and the resolution lines of a circle of twelve fictional people; `places.json` names Home (with its country), Office, Marina and Cabin and leaves the hotels and the anchorages for `places propose`. Phone numbers are in the UK reserved range 07700 900xxx, emails at example.org, the airline is XY, registrations ZZ-. The record is a function of (`days`, `seed`): ids, timestamps, GPS noise, step counts and every text come from one seeded generator and a fixed first day (Monday 1 June 2026), so the same arguments give the same head anywhere. Thirty days is 12,772 lines. `docs/try-it.md`, *Five minutes with a demo record*, walks every reader over it; the README's quick start begins with it; `docs/demo.tape` records it.
- `trips`: a night named by its nearest large airport drops the part after a comma as well as the airport words, so a night off Sandefjord reads `Sandefjord`, not `Sandefjord Airport, Torp`.
- `trips`, "with": the owner is never their own company — `present.owner_of` gathers `owner_id` and `owner_emails` from `logbook.json`, every resolution line that names those, every label they carry, and the record's new `policy/owner.json` (`{"names": [...], "emails": [...], "phones": [...]}`, your other spellings; `init` writes it empty and an older record gets it on the first reading). A calendar attendee counts only for a timed entry held at the stay: its location geocodes within 1 km of the stay's centre (coordinates under `extra.location`, or a `location` naming a place in `places.json`), or it has no location and overlaps the stay by more than an hour; an all-day entry places nobody and a located entry the record cannot place does not count. A transcript participant counts only when the record resolves them to a person (`Speaker A`, `me`, `them`, `Unknown` are nobody). An attendee that does not resolve and has no display name is dropped, and a calendar system address (`calendar.google.com`, `noreply`, `reservations@`, `invite@`) is never a person. At most twelve names, most evidence first. The same rules reach `show place`, `show asset`, `show person` and `rollup people`, which share the with module. (A real record listed the owner, a hotel's reservations address and a diarization label as company.)
- `trips`, the night rule: a night whose stay centre is within 400 m of a place of kind `home` is a night at home whatever that place's radius, so a guest room across the street makes no one-night trip and a trip never starts or ends with such a night. `rollup nights` counts it as home too.
- `trips`, the route: a stay is its named place; else a large airport's name only when the stay is within 2 km of it (it was the nearest within 100 km, so a hotel read as the city); else its coordinates, with `near <place>, x km` for the nearest named place within 5 km. Consecutive route points within 200 m of each other fold into one. `trips.route_of` is the pure function.

### Profiles and spec
- `apple-health`: resting heart rate and HRV are taken as the store keeps them — count/min and ms — no longer multiplied by 60 and 1,000 (a real store showed resting rates in the thousands); heart rate keeps its ×60 (the store holds count/s, the original count/min, checked row for row). Two tables ship in the package: `logbook/tables/airports.csv` (OurAirports, public domain: the 1,150 large airports with scheduled service, IATA, ICAO, name, coordinates and an IANA zone assigned by `scripts/make_airports.py`, the only flights code that touches the network and only at development time) and `logbook/tables/airlines.csv` (IATA ↔ ICAO designators, so Flighty's `SWR` and a calendar's `LX 561` are one flight). `--airports FILE` on `add` and `infer`, or `LOGBOOK_AIRPORTS`, adds a private field or overrides a row (same columns; `icao` and `name` optional).
- SPEC clarifications, round two, no format bump, no hash change (#84): a reader other than `verify` MAY rely on month-file placement; timestamps compare as instants, not text; `tz` names no edition of the zone database and an unknown zone never invalidates a record; a line whose payload does not match its profile is valid and a reader MUST NOT fail on it; the conformance sample tests the chain, not the profiles. New §3.2 *Readers*: a day is ordered by instant then `seq`; retraction lines are not listed on their own day; an alias walk that ends without an entity line names nothing (RFC 0006 rule 6 reworded to match); a collapsed run of points ends at the last point's `end`, else its `at`; read commands MAY refuse a `logbook/0.1` record. Found by logbook-ts while building its `show`. `CONTRIBUTING.md` rewritten: one issue per PR, signed and signed-off commits, synthetic data only, green CI, ADR 0017 for adapters.
- RFC 0012, payload profile `call/v1` (draft): one line per call in a call log — `raw_id` the store's own id, `direction` (`incoming`/`outgoing`), `answered`, `duration_s`, `counterparty` as a source-native `{kind: phone|email|handle, value}` ref (RFC 0006, never resolved here), `service` as the source names it (`cellular`, `facetime`, `facetime-audio`, `whatsapp`, …); `at` the start, `end` the start plus the duration when answered. Tier 1: a call record is metadata about the owner's own time, like a calendar attendee, and carries no one's words. Listed in `rfcs/README.md`.
- RFC 0006: a resolution line may carry `alias_of` — a ref `{ kind, value }` — instead of `entity`: this ref and that ref are the same identity, and the line mints nothing. Rule 6: a reader follows `alias_of` to the target ref's own last line standing, at most 4 hops, stopping on a cycle or at a ref with no line standing, and the line it stops on decides; retraction and last-wins apply to an alias exactly as to an entity line. `logbook/resolve.py` does this, so `show` names a ref that is an alias of a resolved phone without any change of its own (#58).

### Readers and commands
- `logbook serve [--port N]` (`logbook/serve.py`, [docs/serve.md](docs/serve.md)): the record read in a browser, on this machine only. Server-rendered HTML with one inline stylesheet, no script, no font, no image and no link to anywhere but its own paths (a `Content-Security-Policy` of `default-src 'none'` says so to the browser too), every page from the index and the readers the commands use, nothing written. `/day/YYYY-MM-DD` is the Day (`day.read`) as a timeline — the nights, the country, one row per stay, stop, move, flight or run aboard an asset, each row's attachments and company under a toggle (`?open=1` opens them all), what is unplaced, the health line, the sources; `/days?from=&to=` one row per day (`days.read`; the last fortnight without a window; a form and earlier/later links), each a link to its Day; `/trips?year=` the year's trips (`trips.trips`), each linking to its days; `/places`, `/assets` (with the last fix of each, `asset_status.read`) and `/gaps?since=` (`gaps.report`). The server binds 127.0.0.1 and refuses any other host (`--host 0.0.0.0`, `::`, a LAN address, `localhost`) with exit 2 before a socket is opened, and never resolves a name, not even its own. A Day answers in the time `logbook day` takes, through the index, whatever the record's length. Tests: the refusal of every other host, that no page references a URL outside itself (every URL-bearing attribute, the inline style, the headers), the pages on the synthetic persona, a 404 and a 400, that serving writes nothing, and one request over the loopback socket. The text helpers of `logbook/day.py` and `logbook/days.py` the pages reuse are public now (`day.span_text`, `days.night_text`, …).
- `logbook infer keepers [--dry-run]` (`logbook/keepers.py`, producer `keeper-inference`): a `memory` keeper for every photo line its library marked a favourite (`extra.favorite`; the `immich` adapter now keeps `isFavorite` there, `apple-photos` reads as `ios-photos`) and an `art` keeper for every photo in an album named Art (`extra.album` or `extra.albums`, case aside); through `append_many`, so a re-run appends nothing and a retracted keeper is never written again. `logbook keepers [--since DAY] [--until DAY] [--lane memory|art] [--json]` lists the keeper lines standing by day, with the photo's file name. `show <day>` prints the day's keepers under the date as `hero  <file names>` (memory first, `(art)` marked) and each keeper line as `hero photo (<lane>): <file>`.
- `logbook show person|asset|place <name> [--json]` (`logbook/pages.py`): the pages, read from the whole record (the days the owner's track covers). `show person <name>` takes a label (case aside), a unique first name or an entity id and prints the arc: the refs the person resolves from, first and last contact, days together per year, the places shared, open commitments (a placeholder that says `commitment/v1` lines are not read yet), the last ten shared stays with how each was decided, and under `--json` the proposed evidence count and the line ids. `show asset <id>`: the trips aboard (from `trips`), nights, stays and hours aboard, the people aboard, and the summary of the asset's own track when the record holds one (points, stays, moves, distance, first and last fix, the first and last line). `show place <name>`: visits, hours, first and last, per year, the people met there, the photos taken there (photo lines inside a stay at the place), the last ten visits. `show <day>` is unchanged.
- `logbook trips [--year YYYY | --since YYYY-MM-DD --until YYYY-MM-DD] [--airports FILE] [--json]` (`logbook/trips.py`): runs of consecutive days whose overnight stay is outside every home region (places.json, kind `home`) or in transit, from one reading of the window. Each trip: a derived id (`trip:<first day>:<last day>`), its first and last day, the return day (`until`, the day after the last night), nights and nights in transit, the route in night order (the named place, else `near <place>` for a named place within 25 km, else the nearest large airport's name as a coarse city, else coordinates; repeats collapse), the named places visited, the people confirmed present (the with module) between the first day's midnight and the end of the return day, every flight dated inside it and the flights in (dated the first day) and out (dated the return day), `asset` when every night was aboard one asset, and the line ids it rests on. A run made only of in-transit nights is not a trip. Without a place of kind `home` there are no trips, and the command says why. ADR 0019: a trip is never a line, only a reader's output, until the captain names it, and the name is a `note/v1`.
- `logbook rollup places|people`: the two rollups that read company through the with module. `places`: per named place and per asset (the owner's stays aboard it), per year — stays, hours, first and last visit (the stay's start and end day), an asset's nights aboard, and the people confirmed present with their days and lines. `people`: per resolved person, per year — days together (days with confirmed evidence, by the evidence's own day), the last real contact (the last such day), the places shared (a named place, `aboard <asset>`, else coordinates), confirmed and proposed evidence counts and the lines; names that resolve to no person are listed apart under `unresolved`.
- `logbook/present.py`, the "with" module: who was with the owner at a stay. `present(stay, lines, identities)` lists one entry per piece of evidence — a person id when the ref or name resolves through the record's resolution lines (RFC 0006; `resolve.identities_from` gives each ref its entity id and label), else the name or address as the source spelled it — with a confidence, a status and a reason: an attendee of a calendar entry whose span overlaps the stay (confirmed, 0.8 accepted, 0.6 tentative or unanswered, declined absent; `attendee of <title>`), a participant of a transcript recorded inside it (confirmed, 0.9, by email, phone, provider id, else the name against the labels; `spoke in <title>`), a note written inside it that says `with <Name>` (and `<Name>`; confirmed, 1.0; `note says with <name>`), and a face the library tagged in a photo taken inside it (`provider_id` ref `<library>:<person id>`; proposed, 0.5; `face in <file>`). A circle page is listed as a source and names nobody yet. `company` merges the evidence per person, confirmed first, with the sources, reasons and line ids.
- `logbook rollup countries|flights|nights [--year YYYY | --since YYYY-MM-DD --until YYYY-MM-DD] [--airports FILE] [--json]` (`logbook/rollup.py`): the record summed up per year from one reading of the window, clipped to the days the owner's track covers (a day outside them is nothing, not a night in transit). `countries`: days per country per year from the overnight stay, in-transit nights and nights whose country is unknown listed separately, and the method printed with the numbers — `logbook/countries.py`: a place with a `country` (ISO 3166-1 alpha-2, a new optional `places.json` field) whose radius holds the stay decides, else the nearest large airport within 300 km (the airports table) and its zone's country through the bundled `logbook/tables/zones.csv` (the zone database's public-domain `zone.tab`, regenerated by `scripts/make_zones.py`); coarse near borders and far from airports, and the module says so. `flights`: count, kilometres (great-circle between the airports table's coordinates), long-haul (over 3,500 km), unmeasured (an airport the table does not know), by evidence (tracked, inferred, declared), per year, from the flight lines standing (RFC 0013 rule 4), each flight listed with its route and km. `nights`: home, away and in-transit nights per year, nights aboard each asset, and the longest trip (the longest run of consecutive nights not at home); without a place of kind `home` every night is away and the rollup says so. Under `--json` every number carries the ids of the lines it came from: a stay by its first and last location line (one unbroken run), a flight by its line standing. `Index.span(kind)` gives the first and last local day with a line of a kind.
- `logbook places list|add|name|propose` (and `import-takeout`, which moved beside them: the Google Maps saved-places importer now lives at `logbook/adapters/takeout/places.py`): the named places of the record. `places.json` (`logbook/places.py`) maps a name to `{lat, lon, radius_m, kind, tags}`, `kind` one of `home`, `asset-berth`, `other` (absent is `other`; the old three-field shape still reads); home regions are the places of kind `home`, and `derive stays` now marks each night `home` (`"home": true` in the JSON, `· home` in the table) when its stay is a home place or lies in one's radius. `add <name> --lat --lon [--radius] [--kind] [--tags]` edits the file only; `name <lat,lon|stay-id> <name>` adds the place and appends one `note/v1` line, `named <lat>,<lon> as <name>`, so the naming is in the record. `propose [--since] [--until] [--top N] [--json]` is a reader: the owner's unnamed stays of the window (the whole record by default) grouped within 300 m and ranked by hours, each with its stay ids, the nearest known place and the distance, the asset it was aboard, the Google Timeline visits that overlap it when the record holds Takeout timeline lines (place id, semantic type, probability), a suggested name (the visit's semantic type, else `aboard <asset>`, else `near <place>` within 2 km), and under `lines` the ids of its first and last location line and the point count; `--write` asks for each name (Enter accepts the suggestion, `s` skips, `q` stops) and names the accepted ones as `name` does. Every segment of `derive stays --json` now carries a derived `id` (`stay:owner:20260610T1000Z@59.9200,10.7400`: kind, subject, start to the minute, centre) and `lines` (first and last location line id, points). `logbook/reading.py` is the one loader the readers share: a window's lines through the index, the settings, places and assets, the derived stays and nights, and the record's resolutions.
- `policy/import.json`, `{"disabled": [{"source", "reason"}]}`: the sources the owner switched off. `add`, `sync` and `import-backup` skip a disabled source and say so (`<name>: disabled (<reason>); skipped`), `--only` or not, before anything is copied or any variable is asked for; `logbook sources` lists every adapter this build has, file and live, with `enabled` or `disabled (<reason>)`, then any disabled name no adapter carries. Aliases resolve on both sides (`books`, `health`). `init` writes the empty list; a record without the file gets it on the first read. A malformed file exits 2 naming it and nothing is written. README: *What never enters the record* — demo, sample or placeholder data never enters the record; an adapter existing is not a decision to run it.
- `logbook places import-takeout <path> [--write]`: Google Maps' saved and starred places — Takeout's `Maps (your places)/Saved Places.json` (GeoJSON, one Feature per place: the point, the title, the address and business name) and `Saved/<list>.csv` (`Title,Note,URL,Comment`, one list per file: Favourites, Want to go, Starred places, the owner's own; coordinates only when the url carries `/@lat,lon` or `/search/lat,lon`) — proposed as entries of `places.json` (`{lat, lon, category, address?, note?}`, `category` the list's name; `stays.read_places` ignores the extra keys) and written only with `--write`, new names added, an entry already there never changed, a place without coordinates listed and never geocoded (no network). Not lines: a saved place names coordinates, which is what `derive stays` reads from `places.json`. `logbook/places.py`.
- `logbook derive stays [--day YYYY-MM-DD | --since YYYY-MM-DD --until YYYY-MM-DD] [--subject ID] [--dry-run] [--json]`: the first reader of the record. `logbook/stays.py` turns the window's `location/v1` lines into stays, stops and moves, per subject (ADR 0018: the owner first, then each asset), and prints a table in local time (span, kind, place or coordinates, duration, what is attached, aboard) or one JSON object (`window`, `settings`, `subjects`, `segments`, `nights`, `noise_points`). The window runs from the first day's local midnight to 08:00 after the last, so the night is inside it. Points are clustered in time order against an anchor (the cluster's first point, or a named place's centre) within a radius, default 150 m; a single fix away and straight back is GPS noise, dropped and counted; a cluster under `stop_min_s` (3 min) is travel; the same place after a gap under `merge_gap_s` (10 min) is one stay, after a longer gap two stays with a move of no distance between them, printed as `gap`. A cluster is a stay when it lasts `stay_min_s` (20 min) or when anything is attached — an event, transcript, note, call, message or photo whose instant falls inside it, an `end`-bearing line when its span overlaps — evidence promotes (`promoted: true`), duration is the fallback; else a stop, kept and flagged `nothing attached`. Retracted lines never count; counts only, never a line's text. A move spans from one cluster's last point to the next's first: distance along the points between, duration, and a mode from the average speed (walk ≤ 7 km/h, car ≤ 130, train above, flight above 150 km/h or when a gap with no points starts and ends within 8 km of airports, `airports: ["OSL", "BGO"]`); the airports are the flights table (RFC 0013, `flights.Airports`), `--airports FILE` or `LOGBOOK_AIRPORTS` adding to it as for `add flight`. Aboard is derived, never written (ADR 0018 rule 3): the owner's stay is `aboard` an asset when the asset's positions in that span fall within the radius of the stay's centroid, a move when at least half the owner's points have an asset position within the radius at most `aboard_window_s` (5 min) away, a gap between two stays aboard the same asset; aboard a registered asset, or moving as one, the mode is the asset's kind (yacht → boat, aircraft → flight, car → car). The overnight stay of each day is the owner's stay with the longest overlap of the night window (`night: ["22:00", "08:00"]`) when that overlap reaches `stay_min_s`, else the day is `in transit`. Settings live in `<root>/policy/stays.json`, written with the defaults on the first real run and never rewritten (an edited file is honoured); `--dry-run` writes nothing, not even that, and says on stderr which settings apply. `<root>/places.json` (`{"Home": {"lat": 59.91, "lon": 10.75, "radius_m": 120}}`, the radius optional) names a stay and gives the place its own radius. `assets.json` is read through `logbook.assets` for the kinds and names. `--subject <id>` prints one asset's track, `--subject owner` the owner's; an id neither `assets.json` nor a line in the window names exits 2. Nothing is ever appended by this command. `stays.derive(lines, settings, places, assets, tz)` is the pure pass an engine calls without a folder. Tested on synthetic Oslo tracks: GPS noise, an outlier, a short and a long gap at home, a ten-minute cafe stop promoted by one photo, every evidence kind and a retracted message, walk and car by speed, a train to OSL and a gap to BGO as a flight, an overnight at home, a red-eye night in transit, a range of days, a yacht's synthetic AIS track with the owner aboard, the subject filter, an unknown subject, an empty day, and the same lines deriving twice to the same segments.
- `logbook stats --health [--json]`: one row per local day from the `health` lines, read through the index (`Index.of_kind`, a streamed sweep of the files): sleep in hours (the asleep stages — `asleep`, `core`, `deep`, `rem`, never `in_bed` — of the night that ends on the day, summed per device, the longest device taken), steps (per quarter hour the larger device, summed), resting heart rate (the mean of the day's readings). Retracted lines are left out. Never a device, a zone or any other field; `--json` gives `{"days": [...]}`.
- `show` folds one calendar entry that several sources carry into one row: two `event/v1` lines with the same title (case and spacing aside), or naming the same flight in two spellings (`Flight to Zürich (LX 561)`, `Flug LX561 nach Zürich`), starting within five minutes of each other, from different sources, print once, at the first one's time, with the source column naming them all (`ics+ios-calendar`). One calendar holding an entry twice is still two rows. The folded lines leave the day before the runs of location points are collapsed, so a repeat from a second calendar no longer breaks a run in two. Extends SPEC §3.2's run collapse on the reader's side; nothing about the record changes.
- `show` prints a `note/v1` line as its first line, then `… (+N lines)` when there are more (leading blank lines skipped); the whole text, as written, stays behind `--raw`. A day with three long meeting notes reads as three lines again.
- `show`: a run of location points is one source *and one subject* (SPEC §3.2 as clarified); an asset's run is prefixed with its id, so a day at sea reads as the phone's points and the boat's.
- Asset registry (ADR 0018): `<root>/assets.json` names the boats, aircraft and cars whose positions the record tracks as their own subjects, one entry `{id, kind: yacht|aircraft|car, name, mmsi?, icao24?, registration?}` each; `logbook assets add <id> --kind --name [--mmsi] [--icao24] [--registration]` registers one (an id, mmsi or icao24 belongs to one asset; an icao24 is stored lower-case; a bad entry is one line on stderr and exit 2) and `logbook assets list` prints them. A setting of the record, outside the chain, read through `logbook.assets`; unknown keys of the file are preserved.
- `logbook add flight "LX 561 NCE ZRH 2026-09-27 pilot 07:05-08:20 A320 ZZ-ABC"`: the owner's word as a `manual` `flight/v1` line, evidence `declared` — designator, origin, destination, date, then optionally the role (default `passenger`), a departure and arrival clock (local at each airport, recorded as actual; an arrival before the departure is the next local day), an aircraft type and a registration. A sentence that starts `flight` but not with a designator is still a note; one that starts with a designator and does not parse exits 2 with the format. A declared flight the record already holds is merged into it (the role wins) and the console says so.
- `logbook infer flights [--since DAY] [--until DAY] [--airports FILE] [--dry-run]`: `flight/v1` lines, source `flight-inference`, evidence `inferred`, from the record's own evidence: a calendar entry (`event/v1`, its last version standing, not cancelled) whose title names a flight (`LX 561`, `Flight to Zurich (LX 561)`; an airline the table does not know needs the word "flight" or ✈), plus a silence of twenty minutes or more in the location points around it that starts within 8 km of one airport and ends within 8 km of another; the gap's edges are the actual times, the entry's span the scheduled ones, the airports the gap's; a route in the title (`OSL-ZRH`) picks between candidate gaps, else the longest wins. An entry without such a gap is a plan and produces nothing (counted). `extra.event` and `extra.gap` name the entry and the two points. A re-run appends nothing; a flight Flighty already tracked gets the inference attached as an observation.
- `show` prints a flight as `XY 561 OSL → ZRH, arrives 09:24, Airbus A320 LN-XYA, tracked, as pilot` and a flight line another flight line superseded as `superseded by #N`. `Index.by_kind(kind, first_day, last_day)` and `Index.superseded(kind)` (from the `supersedes` column, no rebuild). `adapters.named` resolves the alias `flights` → `flighty`. Tests: the tables (every zone loads), the grammar, the merge in every order, the adapter on a synthetic export (Oslo persona, airline XY), the inference on synthetic tracks around Oslo and Zürich airports, the CLI end to end.
- `verify` streams the record (#28): `Logbook.lines()` is now a merge of the month files — every file open at once, one parsed line from each in a heap keyed by `seq`, the smallest yielded and its file read on — so memory is one line per month file however long the record; the whole-log `export` streams the same way. On a synthetic record of 3,000,000 lines over 120 month files, `verify` went from 72 s and 4.7 GB peak RSS to 54 s and 23 MB, and `export` of the whole log from 26 s and 6.5 GB to 23 s and 29 MB. The writer keeps every file in `seq` order and the merge relies on it; a file that is not (SPEC §3 orders by `seq` wherever a line was found, so such a record can still be valid) raises `UnsortedFile`, and `verify` and the whole-log `export` then read again through the two-pass sorted read `migrate` uses, sixteen bytes a line. `verify --progress` prints one line per month file on stderr as its last line is checked — files finish in the order of their last `seq`, so a backfilled month finishes early — and stdout stays the one line it always was, byte for byte. `verify` still never opens the index.
- Dedupe without the log in memory (#29): `append_many` has deduped through the index since ADR 0007 — one `SELECT` per 10,000-draft batch against the `(source, raw_id)` index, the in-memory set only the batch's own keys, the index extended at every checkpoint so nothing is ever appended past it — and the issue's premise no longer held; this closes it with the measurement: 100,000 drafts already in a 3,000,000-line record are deduped in two to three seconds at 41 MB peak RSS, the same before and after. `show` and `export --day` read only the lines the index locates (checked by a test that fails if either lists or scans the month files). Two `slow` tests (`LOGBOOK_SLOW=1`) build the 3,000,000-line record in a temporary folder and assert that `verify`'s peak RSS on it is within 48 MB of a 1,000,000-line record's and that the dedupe stays under 256 MB, each measured in a process of its own.
- `index.sqlite` schema 3: the `media` column `stats` counts also reads a `payload.content` reference (RFC 0004), so transcripts count as attachments; an existing index is rebuilt once, by the first reader. `show` prints a transcript as `<title> — <participants>; <turns>, <length>`, a participant by the resolution of its email when one exists, never the text. `logbook add` passes `store` (the attachment store), `source`, `tier` and `at` to an adapter whose `run` takes them, and refuses `--source`/`--tier` for one that does not.
- `export crossing --to <destination> --since <RFC3339|last> [--until <RFC3339>] [--tier 1|1,2|1,2,3] [--kinds a,b] [--out <dir>] [--dry-run]` (#77): one `crossing-package/v1` bundle (RFC 0005) for a named circle member, the lines of the half-open window `[since, until)` verbatim in `entries.jsonl`, read through the index and never rewritten; `attachments/<sha256>` copies of every SPEC §1.1 file the store holds (hashed on the way; a missing one stays a reference and is counted); `resolution.jsonl` with every resolution line the exported refs resolve through, alias hops included (RFC 0006), nothing else from outside the window; `manifest.json` with `logbook_head`, `covers`, `recipient`, `tiers`, `counts` (logged, crossed, held back, per tier, per kind, resolutions, attachments), `blobs`, the digest of each file, the tool version, a `review` list of every tier-2 line when tier 2 crosses and a `tier3` warning when tier 3 does. The ceiling per destination lives in `<root>/policy/crossing.json` (ADR 0016), `{"hermes": {"max_tier": 2}}` by default, written by `init` and by the first export; a request above it, or to a destination the file does not name, exits 2 naming the file; tier 3 needs both the file and an explicit `--tier 1,2,3`, and the console says so loudly. Every real export appends one tier-1 `crossing/v1` line, source `logbook` (RFC 0011): destination, window, counts, policy in force, `logbook_head`, and `package_sha256`, the digest of `manifest.json`; then records the window end per destination in `<root>/exports/crossing.json`, which `--since last` reads (the first run without it is refused with the flag to pass). `--dry-run` prints the counts per kind and tier, the attachment bytes and the policy that would apply and writes nothing. A retracted line is held back. `Index.window` locates a window by `at`; `resolve.standing` and `resolve.walk` expose the last-line-standing map and the alias walk `labels` was built on.
- `logbook stats [--json]`: one screen of what a record holds, read through the index in one SELECT per table and nothing from the files: format and head; lines, first and last `at`; lines per kind with first and last local day and distinct sources; lines per source; lines per local year as a bar of one character per ~1% of the busiest year; retractions and the lines they hide; resolution lines and the entities they mint; attachments referenced under `payload.media` or `extra.media` (SPEC §1.1) and how many are present under `attachments/`; and what the run took. Numbers, kinds, sources and dates only, never payload content. `index.sqlite` schema 2 adds the `supersedes`, `entity` and `media` columns it counts; an existing index is rebuilt once, by the first reader.

### Fixes and housekeeping
- `verify --progress` reports the month files in path order, each as `file n of N: <path>: ...` (#120, fixes #101). The merge in `Logbook.lines()` finishes a small file long before a large earlier one, so the lines came out in heap-exhaustion order and a reader could not tell how far the run was; a file that finishes early is now held until every earlier path has, and the counter runs 1, 2, … N.
- `show` no longer fails on an event whose attendee is a string, the shape before RFC 0009: SPEC §3.2 reads it as an `email` ref, named through the record's resolution lines like any other, and anything else is printed as it is (SPEC §5: a reader never fails on a payload it cannot interpret). The conformance sample's first day showed it. `logbook/present.py` no longer raises a SyntaxWarning for an escaped asterisk in its docstring.
- Scrub: `init` prints the record as `~/Logbook` when it is under the home directory, never the expanded path, and `docs/demo.gif` is re-recorded from a throwaway home (the old one showed a real user name); the example flight sentence and the Flighty fixture carry the unassigned registration `ZZ-ABC` instead of a real airline's; the Withings profile ids, the Reminders store names and the Norwegian numbers outside the persona's `+47 9000 000x` block in the fixtures are re-patterned. Nothing in the tree matched the owner's private identifier list.
- Tests no longer see the shell's `LOGBOOK_BACKUP_PASSWORD`: `tests/conftest.py` clears it beside `LOGBOOK_HOME` and the home directory.
- `infer flights` missed every flight of a tracker that keeps logging in the air. The search wanted a silence of twenty minutes between a point at one airport and a point at another; a phone that logs the take-off roll and the climb starts its silence from a point seven kilometres up, near no airport, and one that logs the whole flight is never silent at all, so neither was a flight. Now the search is for a leg: the last point within 8 km of one airport, then the first point within 8 km of a different one, every point between them near no airport, at least twenty minutes apart (`flights.MIN_LEG`, was `MIN_GAP`); the leg's two points are the actual times and `extra.gap` as before, silence in between is usual but not required. `Airports.nearest` looks up the nine one-degree cells around a point (`CELL_KM`) so every point of a day can be placed, not only a gap's edges. "Flug" counts as a flight word beside "flight" and ✈ (`Flug XY561 nach Zürich`). Four calendar entries for one flight (two calendars, two spellings) gave four identical inferences: the dry run said four flights and the real run wrote one and called the other three "already in the record". `flights.reconcile` now drops a draft that repeats an observation earlier in the same stream, and the dry run counts the observations the record already holds the way the real run does, so both say `1 flight from 4 calendar entries`. The skip phrase reads `calendar flights the location points do not confirm`. Found on a real record's September; reproduced on synthetic tracks around Oslo and Zürich airports.
- `granola`: a note Granola made without recording (one empty turn from an instant to the same instant, `duration_s` 0) was still logged as a `transcript/v1` line with an empty transcript stored under it. Now such a note yields only its summary as the `note/v1` line, `raw_id` `granola:<note id>:summary` as ever, `extra.derived_from` set only when the record already holds a transcript for the note (else left out, `derived_from_raw_id` still names it), nothing stored, and the skip counted as `without a recording`. `granola.recorded(line, segments)` is the rule: a segment with words, or a span above zero seconds. Tested with a synthetic note carrying one empty segment.
- `import-backup`: the Safari step reported `safari: History.db not found` on every encrypted backup. The source was registered under `AppDomain-com.apple.mobilesafari`; the phone backs the file up in `HomeDomain` at `Library/Safari/History.db`, and that is where `ios_backup.EXTRAS` now looks. A store is resolved through the `Files` table of `Manifest.db` by domain and `relativePath`, never by a fixed `fileID`; the test plants a synthetic row whose `fileID` is not the SHA-1 a backup would give it and copies the file from where that row points. The encrypted-backup fixture, which had copied the wrong domain, is corrected.
- `import-backup`: a copy is checked against the stored blob, not the manifest's `Size`. An iOS 26.5 backup records a file's size on the phone (`Size`) while the blob it stores is another size, so the first file stopped the import with `copied 29,650,944 bytes, the backup has 35,745,792` although the decryption was exact (blob 29,650,960 = plaintext + 16 bytes of PKCS#7 padding). Now a decrypted copy must equal the blob's length less the padding stripped (`ios_backup_crypto.decrypt_file` returns `Decrypted(written, padding)` and strips valid padding before it honours `Size`; a blob whose last block is not padding fails), a plain copy must equal the blob byte for byte (the manifest's `Size` is now read for an unencrypted backup too), and a copy that matches the blob but not `Size` is one `warning:` line naming the file and both sizes, never an error. `copies.json` records the copy's real `bytes` and, per copy, that `warning`. `Plan.copied` is a list of `ios_backup.Copy`.
- Repository hygiene: `scripts/check_pii.py` is a stdlib-only pre-commit hook that greps every added line of the staged diff for the owner's personal identifiers and fails the commit on a match, printing the file and line but never the text. The identifiers never enter the repository: the hook reads one case-insensitive regex per line from the file `LOGBOOK_PII_PATTERNS` names (default `~/.config/logbook/pii-patterns`); without the file it prints one warning and passes, so CI and other checkouts are unaffected. Tested against a temporary patterns file of synthetic values only. ## 0.3.0 — 2026-09-15
- **BREAKING:** records created by 0.1.0 or 0.2.0 must run `logbook migrate` once before any other command will read or write them (SPEC §3.1).
- Format `logbook/0.2` (SPEC §3.1, ADR 0014): `canonical_json` is now RFC 8785 exactly (UTF-16 key order, ECMAScript float layout; tested against the RFC's vectors). 0.1 hashed floats such as `0.0`, `120.0` and `1e-06` differently, so `verify` and every writer refuse a 0.1 record; `logbook migrate` recomputes `prev`/`hash` in seq order, keeps everything else, records `lineage` in `logbook.json`, appends one `migration/v1` line, keeps the 0.1 files at `logbook-0.1/`.
