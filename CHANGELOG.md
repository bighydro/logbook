# Changelog

## Unreleased
- `imessage` live adapter (#85): `logbook sync imessage` reads the Mac's own `~/Library/Messages/chat.db` (`LOGBOOK_IMESSAGE_DB` names another store, `~` expanded), opened `mode=ro` and only `immutable=1` when that fails, never written and never locked against Messages.app → `message/v1` (RFC 0008) through the file adapter's own mapping, now exposed as `imessage.lines`, so a message imported from the phone backup and the same message read on the Mac have the same line and `raw_id` (the guid) and are deduped; the tapback and group-event skips, the typedstream body, the nanosecond/second dates and the media rule are unchanged. Attachments resolve by the stored paths under the `Attachments` folder beside the store, else the Mac's own `~/Library/Messages/Attachments`; `LOGBOOK_IMESSAGE_HASH_MEDIA=0` skips the hashing as for `add`. The watermark is the newest message date; each pull starts a lookback (24 h, `LOGBOOK_IMESSAGE_LOOKBACK_H`) before it, a first sync with no watermark starts from the record's newest imessage line less the lookback, `--since` is used as given. `sync` reports lines per chat type (`in direct chats`, `in group chats`) with the skips and the attachments hashed or missing. An unreadable database is one line naming Full Disk Access for the terminal as the usual cause, exit 1. The file adapter now cuts `since` in SQL, so rows before it are neither decoded nor hashed. `sync`'s resume line names the source's item (message, point, asset) instead of always "point".
- Repository hygiene: `scripts/check_pii.py` is a stdlib-only pre-commit hook that greps every added line of the staged diff for the owner's personal identifiers and fails the commit on a match, printing the file and line but never the text. The identifiers never enter the repository: the hook reads one case-insensitive regex per line from the file `LOGBOOK_PII_PATTERNS` names (default `~/.config/logbook/pii-patterns`); without the file it prints one warning and passes, so CI and other checkouts are unaffected. Tested against a temporary patterns file of synthetic values only. CLAUDE.md gains the commit routine (author identity, `-s -S`, `git log -1 --format='%G?'` → `G`, how to create the patterns file) and the release routine (grep `__version__` on the tagged commit before `git tag -s`).
- `export crossing --to <destination> --since <RFC3339|last> [--until <RFC3339>] [--tier 1|1,2|1,2,3] [--kinds a,b] [--out <dir>] [--dry-run]` (#77): one `crossing-package/v1` bundle (RFC 0005) for a named circle member, the lines of the half-open window `[since, until)` verbatim in `entries.jsonl`, read through the index and never rewritten; `attachments/<sha256>` copies of every SPEC §1.1 file the store holds (hashed on the way; a missing one stays a reference and is counted); `resolution.jsonl` with every resolution line the exported refs resolve through, alias hops included (RFC 0006), nothing else from outside the window; `manifest.json` with `logbook_head`, `covers`, `recipient`, `tiers`, `counts` (logged, crossed, held back, per tier, per kind, resolutions, attachments), `blobs`, the digest of each file, the tool version, a `review` list of every tier-2 line when tier 2 crosses and a `tier3` warning when tier 3 does. The ceiling per destination lives in `<root>/policy/crossing.json` (ADR 0016), `{"hermes": {"max_tier": 2}}` by default, written by `init` and by the first export; a request above it, or to a destination the file does not name, exits 2 naming the file; tier 3 needs both the file and an explicit `--tier 1,2,3`, and the console says so loudly. Every real export appends one tier-1 `crossing/v1` line, source `logbook` (RFC 0011): destination, window, counts, policy in force, `logbook_head`, and `package_sha256`, the digest of `manifest.json`; then records the window end per destination in `<root>/exports/crossing.json`, which `--since last` reads (the first run without it is refused with the flag to pass). `--dry-run` prints the counts per kind and tier, the attachment bytes and the policy that would apply and writes nothing. A retracted line is held back. `Index.window` locates a window by `at`; `resolve.standing` and `resolve.walk` expose the last-line-standing map and the alias walk `labels` was built on.
- `imessage`: an attachment row with no `filename` is only `extra.media_missing`; `extra.media` is no longer written with a `media_type` and no path, so it always carries `local_path` as its docstring and RFC 0008's media rule say, the fix #74 gave `whatsapp` (its `media_kind` still comes from the mime type). The property test fixes itself to the adapter (#75): its date floor is computed from `APPLE_EPOCH + EARLIEST_DATE` (2010-07-05T05:20:00Z, not the 7th); the media rule holds in the first slot and under `extra.more_media`; a sender may carry the optional `name` RFC 0008 added (#59), never blank, which the test's store now grows a `display_name` column to exercise.
- `whatsapp`: a media row with no `ZMEDIALOCALPATH` is only `extra.media_missing`; `extra.media` is no longer written with a title and no path, so it always carries `local_path` as its docstring and RFC 0008's media rule say. The property test fixes itself to the adapter (#66): its date floor is computed from `APPLE_EPOCH + EARLIEST_DATE` (2010-07-05T05:20:00Z, not the 7th), and a sender may carry the optional `name` RFC 0008 added (#59), never blank.
- CI: a `cross-impl` job on every pull request and push to `main` builds the independent TypeScript implementation ([bighydro/logbook-ts](https://github.com/bighydro/logbook-ts)) at its `main`, checks that its `verify` prints the head in `conformance/expected.json` on `conformance/sample-logbook`, then appends one note to a copy of the sample with the Python CLI and verifies the copy with the TypeScript CLI: the two implementations must agree on a record the other wrote.
- `logbook stats [--json]`: one screen of what a record holds, read through the index in one SELECT per table and nothing from the files: format and head; lines, first and last `at`; lines per kind with first and last local day and distinct sources; lines per source; lines per local year as a bar of one character per ~1% of the busiest year; retractions and the lines they hide; resolution lines and the entities they mint; attachments referenced under `payload.media` or `extra.media` (SPEC §1.1) and how many are present under `attachments/`; and what the run took. Numbers, kinds, sources and dates only, never payload content. `index.sqlite` schema 2 adds the `supersedes`, `entity` and `media` columns it counts; an existing index is rebuilt once, by the first reader.
- `ics` file adapter: any iCalendar file (RFC 5545) — a Google Calendar export or Takeout's `Calendar/` folder, an Apple Calendar export, a saved feed; sniffed by content, so any extension — or a folder of them → `event/v1` (RFC 0009), one line per VEVENT with the same shape `ios-calendar` gives the same event: `at`/`end` from DTSTART/DTEND (or DURATION) in UTC, `tz` the DTSTART's TZID when the zone database knows it (a `/mozilla.org/…/Europe/Oslo` prefix is skipped over; an unknown one is read in the record's zone with the text under `extra.tzid`), floating times in the record's zone, a VALUE=DATE start an all-day event at local midnight ending at the DTEND or the next midnight; `title`, `notes`, `location` (GEO under `extra.location`), `status`, `calendar` from X-WR-CALNAME (else the file name), organizer and attendees as `mailto:` email refs with CN and PARTSTAT; a master's RRULE text as `recurrence` (EXDATE/RDATE under `extra`), a RECURRENCE-ID exception's `recurrence_of`; occurrences never expanded. `raw_id` is `<UID>@<LAST-MODIFIED, else DTSTAMP>` (rule 5), an exception keyed `<UID>/<RECURRENCE-ID>@…`. VEVENTs without a DTSTART, with an unreadable one or one before 1900, or without a UID are skipped and counted, as are VTODO and VJOURNAL blocks. The parser is stdlib only and tolerant: line unfolding, BEGIN/END nesting (an unmatched END is ignored, an open block closes at the end of the file), quoted and multi-valued parameters, TEXT escapes, CRLF or LF, a BOM; what it does not know it passes over. `logbook/adapters/takeout/calendar.py` is the Takeout package's calendar sibling of `location`, delegating to `ics`.
- `import-backup <folder> [--dry-run] [--only names]`: every phone source from an unencrypted iOS backup folder in one go. `logbook/ios_backup.py` reads `Manifest.db` (opened read-only and immutable, so not even a journal appears beside it) and `Manifest.plist`, locates each adapter's store by domain and path — `AddressBook.sqlitedb` → `ios-contacts`, `ContactsV2.sqlite` → `whatsapp-contacts`, `ChatStorage.sqlite` with `Message/` → `whatsapp`, `sms.db` with `Library/SMS/Attachments/` → `imessage`, `Calendar.sqlitedb` → `ios-calendar`, `NoteStore.sqlite` → `ios-notes` — and in that order copies each store with its `-wal`/`-shm` siblings and its media into `<root>/inbox/ios-backup-<udid>/<source>/` under the original names, checks every copy by size, and runs the adapter on the copy (never on the backup, which is never written). A media path that would leave its folder is never copied. Per source: found or not found (a row whose file is missing says so), lines added, skips and notes as `add` reports them; then `verify`. `--dry-run` lists the files and sizes and writes nothing; `--only contacts,whatsapp` limits the run (the fixed order stays). An encrypted backup (`IsEncrypted`) is refused with a one-line message naming Finder's checkbox; a folder without `Manifest.db` exits 2. `LOGBOOK_DIAL_PREFIX` reaches the adapters as with `add`, and a hint is printed when it is unset. The registry gains `adapters.named(name)`.
- `google-takeout-photos` file adapter, the second Takeout sub-adapter: the unzipped `Takeout/Google Photos/` folder (or the Takeout root that holds it, or one album folder) → `photo/v1` (RFC 0002), one line per media file from its JSON sidecar: `at` from `photoTakenTime` (falling back to `creationTime`, counted), `raw_id` the id in the sidecar's Google Photos url else `<album>/<file>`, `provenance` through `googlePhotosOrigin` as a data rule (ADR 0011: `mobileUpload` → `camera`, `fromSharedAlbum` → `received`, else `other`), `lat`/`lon` from `geoData` (then `geoDataExif`) when non-zero, the caption, the album and the tagged names as `extra.people` `{kind: "name", value}` refs, never resolved and never in `payload.people`. A live-photo pair (a still and a video with one stem) is one `camera` line with the motion half under `extra.live_video`. Sidecars are matched by Google's naming (`<file>.json`, `<file>.supplemental-metadata.json`, the truncated and `(1)`-numbered variants), then by `title`, then by a unique prefix; a sidecar with no file is counted and a file with no sidecar is still a line, timed by the file and flagged `extra.no_sidecar`. Media v1 rule as for WhatsApp: the file is hashed into `extra.media` (`sha256`, `bytes`, `local_path`, `media_type`), never copied; `LOGBOOK_TAKEOUT_HASH_MEDIA=0` skips the hashing. `logbook add <folder>` now hands a folder to an adapter that claims it as a whole before walking its files.
- `dawarich` live adapter: `logbook sync dawarich` pulls `GET /api/v1/points` from your own Dawarich server (`LOGBOOK_DAWARICH_URL`, `LOGBOOK_DAWARICH_KEY` as a Bearer header; stdlib urllib, paged until an empty page, yielded oldest first) → `location/v1` (RFC 0001) through the file adapter's own mapping, now exposed as `dawarich.draft`, so a point already imported from an export has the same line and `raw_id` and is deduped. The watermark is the newest point time; each pull starts a lookback (24 h, `LOGBOOK_DAWARICH_LOOKBACK_H`) before it for late batch uploads, and a first sync with no watermark starts from the record's newest dawarich location line (`Index.newest`) less the lookback. Rows without usable coordinates, timestamp or tracker are skipped and counted. `sync` now reports how many pulled lines were already in the record and what the adapter skipped, never moves a watermark backwards, and exits 1 on a malformed response. The registry keeps one file and one live adapter per `NAME`. The shared mapping now drops a non-finite altitude/speed/heading and a heading above 360.
- RFC 0006: a resolution line may carry `alias_of` — a ref `{ kind, value }` — instead of `entity`: this ref and that ref are the same identity, and the line mints nothing. Rule 6: a reader follows `alias_of` to the target ref's own last line standing, at most 4 hops, stopping on a cycle or at a ref with no line standing, and the line it stops on decides; retraction and last-wins apply to an alias exactly as to an entity line. `logbook/resolve.py` does this, so `show` names a ref that is an alias of a resolved phone without any change of its own (#58).
- `whatsapp-contacts` file adapter: an iPhone's WhatsApp ContactsV2.sqlite (also the hashed file in an unencrypted Finder/iTunes backup) → one `resolution/v1` alias line per contact with a linked-device id and a phone number that normalises: `ref` is the lid spelled as the `whatsapp` adapter spells a `@lid` sender, `alias_of` the phone through the shared `adapters/phone.py` (`LOGBOOK_DIAL_PREFIX` as for `ios-contacts`), `label` the name WhatsApp shows, `raw_id` `alias:handle:<lid>` so a later backup appends nothing already aliased. Nothing is minted: the phone's entity comes from the owner's contacts import, before or after. Rows without a lid, without a usable phone, or with a lid already seen are skipped and counted. Opened read-only and immutable, no network (#58).

## 0.4.0 — 2026-09-21
- SPEC §1.1 (ADR 0015): the content-addressed attachment store, `attachments/<sha256>`, optional, write-once, never pruned, outside the hash chain; the `{ sha256, path, bytes, media_type }` reference shape that RFCs 0004, 0005, 0008 and 0010 point at. No format bump; nothing implemented yet.
- SPEC clarifications, no format bump, no hash change: GENESIS named; month-file placement is a writer MUST, not a validity condition; every envelope field present and `end` null, never absent; timestamps UTC with `Z`, fractional seconds hashed verbatim; `seq` decimal unpadded and hex lowercase in the pre-image; the verifier checks §2 as well as the chain; duplicate keys and duplicate `seq` are invalid; only the canonical form is hashed; unknown keys in `logbook.json` are preserved; the write order (lines, then `logbook.json`, then the index). §6 and `conformance/README.md` now state the same tamper-and-delete condition. Found by the clean-room TypeScript implementation.
- The reference is as strict as SPEC §2–3 (#47), no hash change: `verify` names any missing envelope field (`end` is `null`, never absent; `schema/observation.schema.json` now requires it); a line with a duplicate JSON key, at any depth, is invalid on read; writers normalise `at`/`end`/`recorded_at` to UTC with a literal `Z` (an offset is converted, a stamp with no zone is refused); `verify` reports a timestamp with a numeric offset as a WARNING in this release — the record stays valid, exit 0 — and the next release makes it an error; `append`/`append_many` fsync the month files before `logbook.json` is saved.
- `ios-contacts` file adapter: an iPhone's AddressBook.sqlitedb (also the hashed file in an unencrypted Finder/iTunes backup) → `resolution/v1` (RFC 0006), one line per phone number and email address, minting one UUIDv7 per contact as `person` or `company` — how a record gets its people (ADR 0013.2). Opened read-only and immutable; refs are deduped on the normalised value so a later backup appends nothing already resolved; `LOGBOOK_DIAL_PREFIX` completes numbers saved without a country code, dropping one national trunk `0`. `logbook add` now reports every count an adapter tallies, not only the location ones.
- `whatsapp` file adapter: an iPhone's WhatsApp ChatStorage.sqlite (also the hashed file in an unencrypted Finder/iTunes backup) → `message/v1` (RFC 0008), one line per message: chat (direct or group; broadcast lists are groups; status chats skipped), sender as a source-native `phone` or `handle` ref through the new shared `adapters/phone.py` (so a WhatsApp number and an address-book number are the same ref), text, `media_kind`. `raw_id` is `<chat jid>:<stanza id>` so a later backup appends nothing already logged. Media v1 rule: files are never copied into the record; a file present under `Message/` is hashed into `extra.media` (`sha256`, `bytes`, `local_path`) for a later attach pass, a missing one is `extra.media_missing`; `payload.media` is never set (the §1.1 store is not built yet); `LOGBOOK_WHATSAPP_HASH_MEDIA=0` skips the hashing. Streams the store through one cursor, built for a million rows. `logbook add` now also reports what an adapter noted without skipping (media hashed or missing, rows keyed by row id).
- `imessage` file adapter: an iPhone's Messages sms.db (also the hashed file in an unencrypted Finder/iTunes backup) and the chat.db macOS keeps under `~/Library/Messages` → `message/v1` (RFC 0008), one line per message: chat (direct or group), sender as a source-native `phone`, `email` or `handle` ref through the shared `adapters/phone.py`, text, `reply_to`, `media_kind`, `extra.service`. `raw_id` is the message guid, so a later backup appends nothing already logged. A body that iOS 16+ keeps only in `attributedBody` (an NSArchiver typedstream) is decoded by a stdlib-only reader; tapbacks and group events are skipped and counted (rule 1); a date in seconds or nanoseconds since 2001 is read either way. Media v1 rule as for WhatsApp: no file is copied and `payload.media` is never set; a file present under `Attachments/` beside the database is hashed into `extra.media`, a missing one is `extra.media_missing`, further attachments go under `extra.more_media`; `LOGBOOK_IMESSAGE_HASH_MEDIA=0` skips the hashing. One streamed SELECT, opened read-only and immutable.
- `ios-notes` file adapter: an iPhone's Apple Notes NoteStore.sqlite (also the hashed file in an unencrypted Finder/iTunes backup) → `note/v1` (RFC 0010), one line per note at its creation time: `text` decoded from the gzip+protobuf note archive by a stdlib-only walker (field path 2 → 3 → 2), falling back to the snippet when the archive will not decode; `title`, `folder`, `modified_at`; `raw_id` is `<identifier>@<modified_at>` so an edited note is a new line and an unchanged one appends nothing. Password-protected notes are skipped (the body is encrypted); notes marked for deletion are logged with `extra.deleted`; a note with no recoverable text or no usable creation date is skipped. Checklist markers (RFC 0010 rule 3) are not interpreted yet. Opened read-only and immutable, streamed through one cursor.
- `ios-calendar` file adapter: an iPhone's Calendar.sqlitedb (also the hashed file in an unencrypted Finder/iTunes backup) → `event/v1` (RFC 0009), one line per stored entry: span in UTC with the entry's own zone, calendar, title, notes, location (coordinates under `extra.location`), organizer and attendees as email refs with their responses, status. A recurring master carries its rule as RRULE text and a detached occurrence carries `recurrence_of`; occurrences are never expanded. `raw_id` is `<uid>@<last modified>` (rule 5), so an edited entry is a new line next time. Placeholder rows (a start before 1900, such as 1601) and rows with no start are skipped and counted. `supersedes` is never set on import; readers join an edited entry's lines on the bare uid. Every column beyond the start is optional, for other iOS versions. `logbook add` now passes the record's timezone to an adapter whose `run` takes `timezone`, so a floating all-day entry lands at local midnight.
- `show` prints people by name from the record's own resolution lines (RFC 0006): the sender of a message, the organizer and attendees of an event. `Index.resolutions()` yields every resolution line in chain order (no schema change, no rebuild); `logbook/resolve.py` builds one `{(ref.kind, ref.value): label}` map per invocation, skipping retracted lines and the line a later resolution `supersedes`, the last one standing winning for a ref (rule 4). A chat is not an entity: an unnamed group prints its `chat.id` as the source gave it. `show --raw` prints every ref unchanged. `show` still only reads.
- RFC 0008: `sender` gains an optional `name`, the sender's display name as the source shows it (a WhatsApp push name or group-member contact name; iMessage fills it only from a store whose handle table has a `display_name` column), never a resolution. `show` falls back to it when no resolution names the sender, before the direct chat's own name and the raw ref; `--raw` ignores it.
- Tests never see the shell's `LOGBOOK_HOME` or home directory (`HOME`, `USERPROFILE`): an autouse fixture in `tests/conftest.py` pins both to a temporary folder for every test, so a test can never open the real record at `~/Logbook`. Never remove it (CLAUDE.md).

## 0.3.0 — 2026-09-15
- **BREAKING:** records created by 0.1.0 or 0.2.0 must run `logbook migrate` once before any other command will read or write them (SPEC §3.1).
- Format `logbook/0.2` (SPEC §3.1, ADR 0014): `canonical_json` is now RFC 8785 exactly (UTF-16 key order, ECMAScript float layout; tested against the RFC's vectors). 0.1 hashed floats such as `0.0`, `120.0` and `1e-06` differently, so `verify` and every writer refuse a 0.1 record; `logbook migrate` recomputes `prev`/`hash` in seq order, keeps everything else, records `lineage` in `logbook.json`, appends one `migration/v1` line, keeps the 0.1 files at `logbook-0.1/`. The conformance sample is 0.2.
- `index.sqlite`: a disposable SQLite locator of the files (ADR 0001, 0007) — `logbook index` builds it in one streaming pass; `show`, `retract`, `export --day/--days` and `add`/`sync` dedupe go through it and rebuild it when it is missing or stale; `append`/`append_many` extend it at each checkpoint; `verify` and whole-log `export` never read it. `show` now lists a local day (the owner's timezone) with local clock times, as `export --day` always did.
- `sync <source> [--since RFC3339] [--dry-run]` pulls from a live source through the new live-adapter contract (`configure`/`pull`) and keeps its watermark in `state/`; first live adapter: `immich` → `photo/v1` (RFC 0002), stdlib urllib only.

## 0.2.0 — 2026-09-15
- Docs site (MkDocs Material) deployed from main; reproducible demo tape.
- Package published as `openlogbook`; the command is `logbook`.
- `init` and `find` refuse a code checkout (#12).
- `export --day DATE` / `--days FROM TO` write `day-package/v1` directories (ADR 0013 §4); `export/` is ignored.
- `add` takes several paths (`logbook add a.json b.json some/dir`); a path that does not exist is an error (exit 2), never a note.

- `export --days` reads the log once for the whole range instead of once per day.
