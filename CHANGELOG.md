# Changelog

## Unreleased
- `granola`: a note Granola made without recording (one empty turn from an instant to the same instant, `duration_s` 0) was still logged as a `transcript/v1` line with an empty transcript stored under it. Now such a note yields only its summary as the `note/v1` line, `raw_id` `granola:<note id>:summary` as ever, `extra.derived_from` set only when the record already holds a transcript for the note (else left out, `derived_from_raw_id` still names it), nothing stored, and the skip counted as `without a recording`. `granola.recorded(line, segments)` is the rule: a segment with words, or a span above zero seconds. Tested with a synthetic note carrying one empty segment.
- `import-backup`: the Safari step reported `safari: History.db not found` on every encrypted backup. The source was registered under `AppDomain-com.apple.mobilesafari`; the phone backs the file up in `HomeDomain` at `Library/Safari/History.db`, and that is where `ios_backup.EXTRAS` now looks. A store is resolved through the `Files` table of `Manifest.db` by domain and `relativePath`, never by a fixed `fileID`; the test plants a synthetic row whose `fileID` is not the SHA-1 a backup would give it and copies the file from where that row points. The encrypted-backup fixture, which had copied the wrong domain, is corrected.
- Asset registry (ADR 0018): `<root>/assets.json` names the boats, aircraft and cars whose positions the record tracks as their own subjects, one entry `{id, kind: yacht|aircraft|car, name, mmsi?, icao24?, registration?}` each; `logbook assets add <id> --kind --name [--mmsi] [--icao24] [--registration]` registers one (an id, mmsi or icao24 belongs to one asset; an icao24 is stored lower-case; a bad entry is one line on stderr and exit 2) and `logbook assets list` prints them. A setting of the record, outside the chain, read through `logbook.assets`; unknown keys of the file are preserved.
- RFC 0001 `location/v1` amended, backward compatibly: an optional `subject`, the id of an asset in `assets.json`, absent meaning the owner; an asset's positions are its own track and a reader never merges them with the owner's. SPEC §3.2's run rule names the subject (no format bump, no hash change). ADR 0018, assets are subjects, not places: "aboard" is derived downstream, never written on a line.
- `import-backup`: a copy is checked against the stored blob, not the manifest's `Size`. An iOS 26.5 backup records a file's size on the phone (`Size`) while the blob it stores is another size, so the first file stopped the import with `copied 29,650,944 bytes, the backup has 35,745,792` although the decryption was exact (blob 29,650,960 = plaintext + 16 bytes of PKCS#7 padding). Now a decrypted copy must equal the blob's length less the padding stripped (`ios_backup_crypto.decrypt_file` returns `Decrypted(written, padding)` and strips valid padding before it honours `Size`; a blob whose last block is not padding fails), a plain copy must equal the blob byte for byte (the manifest's `Size` is now read for an unencrypted backup too), and a copy that matches the blob but not `Size` is one `warning:` line naming the file and both sizes, never an error. `copies.json` records the copy's real `bytes` and, per copy, that `warning`. `Plan.copied` is a list of `ios_backup.Copy`.
- SPEC clarifications, round two, no format bump, no hash change (#84): a reader other than `verify` MAY rely on month-file placement; timestamps compare as instants, not text; `tz` names no edition of the zone database and an unknown zone never invalidates a record; a line whose payload does not match its profile is valid and a reader MUST NOT fail on it; the conformance sample tests the chain, not the profiles. New §3.2 *Readers*: a day is ordered by instant then `seq`; retraction lines are not listed on their own day; an alias walk that ends without an entity line names nothing (RFC 0006 rule 6 reworded to match); a collapsed run of points ends at the last point's `end`, else its `at`; read commands MAY refuse a `logbook/0.1` record. Found by logbook-ts while building its `show`. `CONTRIBUTING.md` rewritten: one issue per PR, signed and signed-off commits, synthetic data only, green CI, ADR 0017 for adapters.
- `verify` streams the record (#28): `Logbook.lines()` is now a merge of the month files — every file open at once, one parsed line from each in a heap keyed by `seq`, the smallest yielded and its file read on — so memory is one line per month file however long the record; the whole-log `export` streams the same way. On a synthetic record of 3,000,000 lines over 120 month files, `verify` went from 72 s and 4.7 GB peak RSS to 54 s and 23 MB, and `export` of the whole log from 26 s and 6.5 GB to 23 s and 29 MB. The writer keeps every file in `seq` order and the merge relies on it; a file that is not (SPEC §3 orders by `seq` wherever a line was found, so such a record can still be valid) raises `UnsortedFile`, and `verify` and the whole-log `export` then read again through the two-pass sorted read `migrate` uses, sixteen bytes a line. `verify --progress` prints one line per month file on stderr as its last line is checked — files finish in the order of their last `seq`, so a backfilled month finishes early — and stdout stays the one line it always was, byte for byte. `verify` still never opens the index.
- Dedupe without the log in memory (#29): `append_many` has deduped through the index since ADR 0007 — one `SELECT` per 10,000-draft batch against the `(source, raw_id)` index, the in-memory set only the batch's own keys, the index extended at every checkpoint so nothing is ever appended past it — and the issue's premise no longer held; this closes it with the measurement: 100,000 drafts already in a 3,000,000-line record are deduped in two to three seconds at 41 MB peak RSS, the same before and after. `show` and `export --day` read only the lines the index locates (checked by a test that fails if either lists or scans the month files). Two `slow` tests (`LOGBOOK_SLOW=1`) build the 3,000,000-line record in a temporary folder and assert that `verify`'s peak RSS on it is within 48 MB of a 1,000,000-line record's and that the dedupe stays under 256 MB, each measured in a process of its own.
- `import-backup` reads an encrypted iOS backup (`IsEncrypted` with a `BackupKeyBag`). `logbook/ios_backup_crypto.py` implements the publicly documented keybag format: TLV records; the passcode key by PBKDF2-HMAC-SHA256 over `DPSL`/`DPIC` then PBKDF2-HMAC-SHA1 over `SALT`/`ITER` (a keybag from before iOS 10.2, without `DPSL`/`DPIC`, does the SHA-1 pass alone); class keys unwrapped per RFC 3394 with the passcode key (`WRAP` bit 2; a device-wrapped class, bit 1, stays unavailable); `ManifestKey` and each row's `EncryptionKey` (in the `file` column's NSKeyedArchiver plist) as a 4-byte protection class plus a 40-byte wrapped key; files and `Manifest.db` AES-256-CBC with a zero IV, PKCS#7 padding stripped or the manifest's `Size` honoured, decrypted in 1 MiB chunks, never whole in memory. The password comes only from `LOGBOOK_BACKUP_PASSWORD` — never a flag, never printed, never in a message or a file; the keybag is checked first, so a wrong password exits 2 before any file is touched. `Manifest.db` is decrypted into `<root>/inbox/ios-backup-<udid>/` and every copy is decrypted on the way to the same layout as for an unencrypted backup, so every adapter runs unchanged; each copy is checked against the plaintext size. Stores only an encrypted backup carries (`ios_backup.EXTRAS`) are copied out with no adapter yet and say so: `health/healthdb_secure.sqlite`, `health/healthdb.sqlite`, `calls/CallHistory.storedata`, `safari/History.db` (`--only health,calls,safari` names them). The inbox gains `copies.json` for every backup, encrypted or not: per copy its domain, path, copy, bytes, `encrypted` and `protection_class`, merged over earlier runs of other sources, never a key. `cryptography` is the optional extra `openlogbook[encrypted]`, imported lazily; an encrypted backup without it prints one line with `pip install "openlogbook[encrypted]"` and exits 2; the unencrypted path has no new dependency. Tested on a synthetic backup built in the test — a keybag from a test password with ten iterations, class and file keys wrapped, `Manifest.db`, `sms.db`, an attachment, a Health and a Safari store encrypted — proving the round trip byte for byte, the wrong-password refusal, the missing-extra message and the older keybag; never a real backup.
- RFC 0012, payload profile `call/v1` (draft): one line per call in a call log — `raw_id` the store's own id, `direction` (`incoming`/`outgoing`), `answered`, `duration_s`, `counterparty` as a source-native `{kind: phone|email|handle, value}` ref (RFC 0006, never resolved here), `service` as the source names it (`cellular`, `facetime`, `facetime-audio`, `whatsapp`, …); `at` the start, `end` the start plus the duration when answered. Tier 1: a call record is metadata about the owner's own time, like a calendar attendee, and carries no one's words. Listed in `rfcs/README.md`.

Tests on a synthetic store built by the test: incoming, outgoing and missed, FaceTime video and audio against cellular and a WhatsApp call, the epoch conversion, a blob address, the dial prefix, unmapped columns under `extra`, dedupe on re-import, the CLI by name and by sniff, the encrypted backup round trip, and a property test over random rows.

- `gcal` live adapter: `logbook sync gcal` pulls Google Calendar's private iCal feeds (`LOGBOOK_GCAL_URLS`, comma-separated, each optionally `name=url`; stdlib urllib, fetched whole) → `event/v1` (RFC 0009) through the ics adapter's own reader, now exposed as `ics.lines(text, name, counts, timezone)`, so an event imported from a calendar export and the same event pulled by URL are the same line with the same `raw_id` (`<UID>@<LAST-MODIFIED>`) and `source` (`ics`) and are deduped (ADR 0017); recurring masters and materialised occurrences, all-day and floating times (in the record's zone, which `sync` now passes to a `pull` that takes `timezone`) are unchanged. The feed's X-WR-CALNAME names the calendar as for a file; a given name applies only to a feed without one. The watermark is the newest last-modified time seen; each pull keeps the events changed since a lookback (24 h, `LOGBOOK_GCAL_LOOKBACK_H`) before it and the dedupe absorbs the overlap; a first sync reads everything; `--since` is used as given. `sync` reports seen and new per calendar (a live adapter's optional `group(draft)`; `append_many` gains a `skipped` callback for the drafts it deduped) and, on `--dry-run`, seen per calendar. A calendar that fails (an HTTP error, an unreachable host, a body that is not a calendar) is one line on stderr naming the calendar by its given name or a short hash of its URL, never the URL; the other calendars are still pulled and written, the watermark is kept, the exit is 1 (a live adapter's optional `failed` list). The URLs never appear in the config's repr or any output.
- `imessage` live adapter (#85): `logbook sync imessage` reads the Mac's own `~/Library/Messages/chat.db` (`LOGBOOK_IMESSAGE_DB` names another store, `~` expanded), opened `mode=ro` and only `immutable=1` when that fails, never written and never locked against Messages.app → `message/v1` (RFC 0008) through the file adapter's own mapping, now exposed as `imessage.lines`, so a message imported from the phone backup and the same message read on the Mac have the same line and `raw_id` (the guid) and are deduped; the tapback and group-event skips, the typedstream body, the nanosecond/second dates and the media rule are unchanged. Attachments resolve by the stored paths under the `Attachments` folder beside the store, else the Mac's own `~/Library/Messages/Attachments`; `LOGBOOK_IMESSAGE_HASH_MEDIA=0` skips the hashing as for `add`. The watermark is the newest message date; each pull starts a lookback (24 h, `LOGBOOK_IMESSAGE_LOOKBACK_H`) before it, a first sync with no watermark starts from the record's newest imessage line less the lookback, `--since` is used as given. `sync` reports lines per chat type (`in direct chats`, `in group chats`) with the skips and the attachments hashed or missing. An unreadable database is one line naming Full Disk Access for the terminal as the usual cause, exit 1. The file adapter now cuts `since` in SQL, so rows before it are neither decoded nor hashed. `sync`'s resume line names the source's item (message, point, asset) instead of always "point".
- `transcript` file adapter (#78): `logbook add transcript <file|folder> [--source <name>] [--tier 1|2|3] [--at <RFC3339>]` → `transcript/v1` (RFC 0004), one line per file. Reads JSON already in transcript/v1 shape — the interchange format for any tool, a `logbook export` line minus the chain fields, the payload kept as given, an inline `content.text` stored and replaced by its reference — WebVTT and SRT (every cue a turn; the speaker from the `<v Name>` voice tag or a leading `Name:`, else unknown; the cues' offsets give `end`), and Markdown or plain text with `Speaker: text` lines, a following line continuing the turn, and an optional front-matter block for `title`, `started_at`, `ended_at`, `participants` (`Name <email>`), a `# heading` as the title. VTT, SRT and transcript JSON are sniffed by content, so `logbook add meeting.vtt` works without the keyword; Markdown and text only through it. The file's own bytes are the SPEC §1.1 attachment: the first writer of `attachments/<sha256>` (`Logbook.attach`, `logbook/attachments.py`: write-once, a mismatching file is an error, never overwritten); `raw_id` is `<source>:<sha256>` unless the JSON brings one; the start is the front matter's, else `--at`, else a date and time in the file name (`2026-03-01T13-00-00Z …`, Zoom's `GMT20260301-130000_…`, `2026-03-01 1300 …` in the record's zone, a bare date at local midnight), else the file is skipped and counted. Tier 3 by default: a transcript carries other people's words in full. `participants` are the front matter's, then every speaker label, source-native, never resolved; `extra` carries `format`, `file`, `turns`, `speakers`, `unattributed` and `duration_s`. `transcript.draft` is the one mapping every transcript source shares (ADR 0017).
- `granola` live adapter (#78): `logbook sync granola` pulls Granola's public API v1 (`LOGBOOK_GRANOLA_KEY`, a `grn_` key from Settings → Connectors → API keys, Business and Enterprise plans; `LOGBOOK_GRANOLA_URL`, default `https://public-api.granola.ai/v1`): `GET /notes?created_after=` with cursor paging, `GET /notes/{id}?include=transcript`, and `GET /notes/{id}/transcript` paged when the note answers 413 TRANSCRIPT_TOO_LARGE. One `transcript/v1` line per recording through `transcript.draft`, so a transcript exported by hand as transcript/v1 JSON and the same one pulled here are one line: `raw_id` `granola:<note id>`, `at`/`end` the segments' span (else the calendar event's, else `created_at`), `participants` the attendees as Granola names them plus any speaker label they do not cover (never resolved), `content` the segments as JSON under `attachments/`, `source_uri` the note's web url, `extra.folders`. Granola's AI summary is a model's words, so it is never `payload.summary`: it is a second line, `note/v1`, source `granola`, tier 2, `raw_id` `granola:<note id>:summary`, `extra.derived = true` and `extra.derived_from` the transcript line's id — the one already in the record when a hand export came first (`Index.line_id`, asked through the new `lookup` callback), else the one this pull mints (`append_many` now keeps an `id` a draft brings); `LOGBOOK_GRANOLA_SUMMARIES=0` skips it. The watermark is the recording's end; `resume` looks back 24 h (`LOGBOOK_GRANOLA_LOOKBACK_H`), a first sync continues from the record's newest granola transcript, `--since` is used as given. Every request is retried once on a connection failure, a timeout, 429 or a 5xx, then the sync exits 1 with a message naming the request (a 401 names the variable) and nothing has been written: the whole pull is fetched before the first line is yielded, attachments are stored only as their line is yielded, and a dry run stores nothing. `sync --dry-run` now prints the count per kind when a source yields more than one. The key is sent only in the `Authorization` header, never in a URL, never printed. Tested against a fake of the API serving synthetic Oslo notes; no network.
- ADR 0017: backfill and live share one mapping — every source adapter has a file mode and, where the source offers it, a live mode, both producing identical lines with the same `raw_id`, so backfilled and live lines dedupe; the rule for every adapter from now on, `dawarich` and `imessage` the existing examples.
- `index.sqlite` schema 3: the `media` column `stats` counts also reads a `payload.content` reference (RFC 0004), so transcripts count as attachments; an existing index is rebuilt once, by the first reader. `show` prints a transcript as `<title> — <participants>; <turns>, <length>`, a participant by the resolution of its email when one exists, never the text. `logbook add` passes `store` (the attachment store), `source`, `tier` and `at` to an adapter whose `run` takes them, and refuses `--source`/`--tier` for one that does not.
- Repository hygiene: `scripts/check_pii.py` is a stdlib-only pre-commit hook that greps every added line of the staged diff for the owner's personal identifiers and fails the commit on a match, printing the file and line but never the text. The identifiers never enter the repository: the hook reads one case-insensitive regex per line from the file `LOGBOOK_PII_PATTERNS` names (default `~/.config/logbook/pii-patterns`); without the file it prints one warning and passes, so CI and other checkouts are unaffected. Tested against a temporary patterns file of synthetic values only. - `export crossing --to <destination> --since <RFC3339|last> [--until <RFC3339>] [--tier 1|1,2|1,2,3] [--kinds a,b] [--out <dir>] [--dry-run]` (#77): one `crossing-package/v1` bundle (RFC 0005) for a named circle member, the lines of the half-open window `[since, until)` verbatim in `entries.jsonl`, read through the index and never rewritten; `attachments/<sha256>` copies of every SPEC §1.1 file the store holds (hashed on the way; a missing one stays a reference and is counted); `resolution.jsonl` with every resolution line the exported refs resolve through, alias hops included (RFC 0006), nothing else from outside the window; `manifest.json` with `logbook_head`, `covers`, `recipient`, `tiers`, `counts` (logged, crossed, held back, per tier, per kind, resolutions, attachments), `blobs`, the digest of each file, the tool version, a `review` list of every tier-2 line when tier 2 crosses and a `tier3` warning when tier 3 does. The ceiling per destination lives in `<root>/policy/crossing.json` (ADR 0016), `{"hermes": {"max_tier": 2}}` by default, written by `init` and by the first export; a request above it, or to a destination the file does not name, exits 2 naming the file; tier 3 needs both the file and an explicit `--tier 1,2,3`, and the console says so loudly. Every real export appends one tier-1 `crossing/v1` line, source `logbook` (RFC 0011): destination, window, counts, policy in force, `logbook_head`, and `package_sha256`, the digest of `manifest.json`; then records the window end per destination in `<root>/exports/crossing.json`, which `--since last` reads (the first run without it is refused with the flag to pass). `--dry-run` prints the counts per kind and tier, the attachment bytes and the policy that would apply and writes nothing. A retracted line is held back. `Index.window` locates a window by `at`; `resolve.standing` and `resolve.walk` expose the last-line-standing map and the alias walk `labels` was built on.

- CI: a `cross-impl` job on every pull request and push to `main` builds the independent TypeScript implementation ([bighydro/logbook-ts](https://github.com/bighydro/logbook-ts)) at its `main`, checks that its `verify` prints the head in `conformance/expected.json` on `conformance/sample-logbook`, then appends one note to a copy of the sample with the Python CLI and verifies the copy with the TypeScript CLI: the two implementations must agree on a record the other wrote.
- `logbook stats [--json]`: one screen of what a record holds, read through the index in one SELECT per table and nothing from the files: format and head; lines, first and last `at`; lines per kind with first and last local day and distinct sources; lines per source; lines per local year as a bar of one character per ~1% of the busiest year; retractions and the lines they hide; resolution lines and the entities they mint; attachments referenced under `payload.media` or `extra.media` (SPEC §1.1) and how many are present under `attachments/`; and what the run took. Numbers, kinds, sources and dates only, never payload content. `index.sqlite` schema 2 adds the `supersedes`, `entity` and `media` columns it counts; an existing index is rebuilt once, by the first reader.
- `ics` file adapter: any iCalendar file (RFC 5545) — a Google Calendar export or Takeout's `Calendar/` folder, an Apple Calendar export, a saved feed; sniffed by content, so any extension — or a folder of them → `event/v1` (RFC 0009), one line per VEVENT with the same shape `ios-calendar` gives the same event: `at`/`end` from DTSTART/DTEND (or DURATION) in UTC, `tz` the DTSTART's TZID when the zone database knows it (a `/mozilla.org/…/Europe/Oslo` prefix is skipped over; an unknown one is read in the record's zone with the text under `extra.tzid`), floating times in the record's zone, a VALUE=DATE start an all-day event at local midnight ending at the DTEND or the next midnight; `title`, `notes`, `location` (GEO under `extra.location`), `status`, `calendar` from X-WR-CALNAME (else the file name), organizer and attendees as `mailto:` email refs with CN and PARTSTAT; a master's RRULE text as `recurrence` (EXDATE/RDATE under `extra`), a RECURRENCE-ID exception's `recurrence_of`; occurrences never expanded. `raw_id` is `<UID>@<LAST-MODIFIED, else DTSTAMP>` (rule 5), an exception keyed `<UID>/<RECURRENCE-ID>@…`. VEVENTs without a DTSTART, with an unreadable one or one before 1900, or without a UID are skipped and counted, as are VTODO and VJOURNAL blocks. The parser is stdlib only and tolerant: line unfolding, BEGIN/END nesting (an unmatched END is ignored, an open block closes at the end of the file), quoted and multi-valued parameters, TEXT escapes, CRLF or LF, a BOM; what it does not know it passes over. `logbook/adapters/takeout/calendar.py` is the Takeout package's calendar sibling of `location`, delegating to `ics`.
- `import-backup <folder> [--dry-run] [--only names]`: every phone source from an unencrypted iOS backup folder in one go. `logbook/ios_backup.py` reads `Manifest.db` (opened read-only and immutable, so not even a journal appears beside it) and `Manifest.plist`, locates each adapter's store by domain and path — `AddressBook.sqlitedb` → `ios-contacts`, `ContactsV2.sqlite` → `whatsapp-contacts`, `ChatStorage.sqlite` with `Message/` → `whatsapp`, `sms.db` with `Library/SMS/Attachments/` → `imessage`, `Calendar.sqlitedb` → `ios-calendar`, `NoteStore.sqlite` → `ios-notes` — and in that order copies each store with its `-wal`/`-shm` siblings and its media into `<root>/inbox/ios-backup-<udid>/<source>/` under the original names, checks every copy by size, and runs the adapter on the copy (never on the backup, which is never written). A media path that would leave its folder is never copied. Per source: found or not found (a row whose file is missing says so), lines added, skips and notes as `add` reports them; then `verify`. `--dry-run` lists the files and sizes and writes nothing; `--only contacts,whatsapp` limits the run (the fixed order stays). An encrypted backup (`IsEncrypted`) is refused with a one-line message naming Finder's checkbox; a folder without `Manifest.db` exits 2. `LOGBOOK_DIAL_PREFIX` reaches the adapters as with `add`, and a hint is printed when it is unset. The registry gains `adapters.named(name)`.
- `google-takeout-photos` file adapter, the second Takeout sub-adapter: the unzipped `Takeout/Google Photos/` folder (or the Takeout root that holds it, or one album folder) → `photo/v1` (RFC 0002), one line per media file from its JSON sidecar: `at` from `photoTakenTime` (falling back to `creationTime`, counted), `raw_id` the id in the sidecar's Google Photos url else `<album>/<file>`, `provenance` through `googlePhotosOrigin` as a data rule (ADR 0011: `mobileUpload` → `camera`, `fromSharedAlbum` → `received`, else `other`), `lat`/`lon` from `geoData` (then `geoDataExif`) when non-zero, the caption, the album and the tagged names as `extra.people` `{kind: "name", value}` refs, never resolved and never in `payload.people`. A live-photo pair (a still and a video with one stem) is one `camera` line with the motion half under `extra.live_video`. Sidecars are matched by Google's naming (`<file>.json`, `<file>.supplemental-metadata.json`, the truncated and `(1)`-numbered variants), then by `title`, then by a unique prefix; a sidecar with no file is counted and a file with no sidecar is still a line, timed by the file and flagged `extra.no_sidecar`. Media v1 rule as for WhatsApp: the file is hashed into `extra.media` (`sha256`, `bytes`, `local_path`, `media_type`), never copied; `LOGBOOK_TAKEOUT_HASH_MEDIA=0` skips the hashing. `logbook add <folder>` now hands a folder to an adapter that claims it as a whole before walking its files.
- `dawarich` live adapter: `logbook sync dawarich` pulls `GET /api/v1/points` from your own Dawarich server (`LOGBOOK_DAWARICH_URL`, `LOGBOOK_DAWARICH_KEY` as a Bearer header; stdlib urllib, paged until an empty page, yielded oldest first) → `location/v1` (RFC 0001) through the file adapter's own mapping, now exposed as `dawarich.draft`, so a point already imported from an export has the same line and `raw_id` and is deduped. The watermark is the newest point time; each pull starts a lookback (24 h, `LOGBOOK_DAWARICH_LOOKBACK_H`) before it for late batch uploads, and a first sync with no watermark starts from the record's newest dawarich location line (`Index.newest`) less the lookback. Rows without usable coordinates, timestamp or tracker are skipped and counted. `sync` now reports how many pulled lines were already in the record and what the adapter skipped, never moves a watermark backwards, and exits 1 on a malformed response. The registry keeps one file and one live adapter per `NAME`. The shared mapping now drops a non-finite altitude/speed/heading and a heading above 360.
- RFC 0006: a resolution line may carry `alias_of` — a ref `{ kind, value }` — instead of `entity`: this ref and that ref are the same identity, and the line mints nothing. Rule 6: a reader follows `alias_of` to the target ref's own last line standing, at most 4 hops, stopping on a cycle or at a ref with no line standing, and the line it stops on decides; retraction and last-wins apply to an alias exactly as to an entity line. `logbook/resolve.py` does this, so `show` names a ref that is an alias of a resolved phone without any change of its own (#58).
- `whatsapp-contacts` file adapter: an iPhone's WhatsApp ContactsV2.sqlite (also the hashed file in an unencrypted Finder/iTunes backup) → one `resolution/v1` alias line per contact with a linked-device id and a phone number that normalises: `ref` is the lid spelled as the `whatsapp` adapter spells a `@lid` sender, `alias_of` the phone through the shared `adapters/phone.py` (`LOGBOOK_DIAL_PREFIX` as for `ios-contacts`), `label` the name WhatsApp shows, `raw_id` `alias:handle:<lid>` so a later backup appends nothing already aliased. Nothing is minted: the phone's entity comes from the owner's contacts import, before or after. Rows without a lid, without a usable phone, or with a lid already seen are skipped and counted. Opened read-only and immutable, no network (#58).
