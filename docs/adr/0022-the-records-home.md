# ADR 0022 — The record has one home; everything else reads

Status: accepted · 2026-10-09 · extends ADR 0001, ADR 0016 and ADR 0020

**Context.** ADR 0001 made the folder the truth and ADR 0003 made it one log; ADR 0016 put the ceiling for every crossing in the record itself and made every crossing a line. What none of them says is *where the folder lives* once more than one machine wants it. The owner's set-up now has four kinds of device: one always-on machine at home, a laptop, phones, and an agent on a private VPS that runs the daily loop. The sync schedule (`sync --install-schedule`), the MCP server and the local models all assume a machine that has the record's files; the writer lock (#237) assumes one process at a time on one machine; `doctor` already refuses a record under a sync client's folder because that client rewrites files underneath the writer and puts the record on someone else's server. Two writable copies would need a merge the chain does not have (SPEC §3: one head, append only), and a bridge that carries messages through a cloud machine would carry tier-2 content through it before the record has sealed anything (ADR 0020). The question is not new, but every answer so far was a convention nobody wrote down, and the first collaborator and the first cloud model will each need to be told the same thing.

**Decision.**

1. **One machine is the record's home.** It holds the only writable copy. It runs the sync schedule, the MCP server and the local models, and it serves the Day page over the owner's private network (the tailnet), never from a cloud machine when the page shows tier-2 content. Messaging reaches it through Beeper's on-device connections today and may reach it through a self-hosted Matrix homeserver with mautrix bridges later; the lines are the same either way, so the choice of carrier is the owner's and not the format's.
2. **Every other device is a reader.** A phone or a laptop holds a sealed backup (`logbook backup`) or an export, or reads through the MCP server under the `mcp` ceiling. There is no second writable copy, and the record folder is never in a file sync (iCloud Drive, Dropbox, Syncthing or any other): `doctor` fails the first and nothing here softens that.
3. **Orchestrators reach the record only through the crossing.** An agent on a VPS, a cron, a phone: each reads with the read tools under `policy/crossing.json` and writes with the few write tools the owner allows by name, today the day's signature and its note. They never hold the record's files, never get a copy of the key, and never run a writer of their own.
4. **Sources come to the home.** A messaging app connects on the home machine, as a linked device or a local database (iMessage, Telegram, Signal, WhatsApp), and writes through `sync` under the lock. A bridge on a cloud machine would carry tier-2 content through that machine, so it is not done.
5. **A collaborator's access is a separate OS user on the home machine**, after sealing at rest (ADR 0020), with the MCP socket and the tailnet and not the record's files. Never on the owner's working laptop.
6. **The cloud ceiling is the owner's and is written down.** Every cloud model or service that may see record content has its own entry in `policy/crossing.json` with a `max_tier` and, where the access is temporary, an `until` date (`{"cloud-model": {"max_tier": 2, "until": "2026-12-31"}}`). The entry holds through that day; an entry that has expired counts as tier 0, and `doctor` names it. There is no entry that covers "the cloud"; each service is named.
7. **The home is recorded and checked.** `sync --install-schedule` writes `state/home.json` with the hostname and the date; `doctor` passes when it runs on that host or when no home is set, and warns on any other machine that writers belong on the home. The writer lock records the hostname beside the pid and the command, so a lock left by another machine is read as such.

**Alternatives considered.**

- *The record on the VPS, beside the agent.* The agent would then hold the files, the key and the ceiling in one place that is not the owner's, and every tier would be one misconfiguration from the cloud. The crossing exists so that an orchestrator never needs the files; moving the files to it inverts ADR 0016.
- *The record synced between the laptop and the home machine.* Two writers on one chain need a merge the format refuses to have, and a sync client is exactly what `doctor` fails a record for. A conflict would be found at the next `verify`, after the files were already wrong.
- *The laptop as the home.* A laptop is closed, asleep and away; the schedule, the MCP and the local models want a machine that is on, and the collaborator's OS user does not belong on the machine the owner works at. It may be the home for now (consequences), but it is not the design.

**Consequences.** The owner's laptop may be the home for now: `sync --install-schedule` there names it, and `doctor` on the always-on machine says so until the record moves. Home moves by copying the record once (`logbook backup`, then `backup restore`, or one `cp`) and running `sync --install-schedule` on the new machine, which names it; never by syncing, and the old copy becomes a reader or is deleted. A phone is a reader and a camera, never a writer, until the day a reader on it can write through the crossing. Every cloud model the owner tries is one line in the policy with a date, and an experiment the owner forgets to end ends itself. The collaborator's first day is an OS account and a tailnet invitation, not a copy of the folder. What this ADR does not decide: the transport of the shared page (ARCHITECTURE, "The circle"), and whether the MCP server will one day listen on the tailnet itself rather than over stdio on the home; both are RFCs when they come.
