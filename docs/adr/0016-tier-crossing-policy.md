# ADR 0016 — The crossing ceiling is the owner's setting; a crossing is never invisible

Status: accepted · 2026-09-29

**Context.** A crossing package (RFC 0005) hands verbatim lines, payloads included, to a named member of the circle. RFC 0005 states the tier policy in prose: tier 1 crosses automatically, tier 2 after a batched review, tier 3 never. Written as a constant in the code, that policy would be wrong twice: too strict for an owner whose circumstances change (a partner who should see the money lines, a doctor who should see the health lines), and too loose the moment anyone edits it, because nothing would then say that the ceiling moved. The first consumer, Hermes, runs nightly and unattended; whatever it can pull must be exactly what the owner meant to let cross, and the record must show every time it crossed.

**Decision.**

1. **The ceiling is a setting in the record, not a constant.** `<root>/policy/crossing.json` maps a destination to the highest tier that may cross to it: `{"hermes": {"max_tier": 2}}`. `logbook init` writes that default; so does the first real export into a record that has none. The code reads the file and never decides a ceiling on its own. A destination the file does not name has no ceiling and cannot receive a crossing until the owner adds it.
2. **Every export names its destination and the tiers it asks for.** `logbook export crossing --to <destination> --tier 1|1,2|1,2,3`. A request above the destination's ceiling exits non-zero with a message that names the file, so the owner raises the ceiling deliberately, in the record, or does not.
3. **Tier 1 crosses by default; tier 2 only when asked; tier 3 only when both the policy allows it and the owner types `--tier 1,2,3`.** A policy edit alone never lets tier 3 cross. When tier 2 crosses, the manifest carries a `review` section listing every tier-2 line in the package by id, kind, source and time, so the batch can be reviewed as a whole (ADR 0005: one message, never line by line). When tier 3 crosses, the manifest and the console say so in words nobody can miss.
4. **A crossing is never invisible.** Every real export appends one `crossing/v1` line (RFC 0011) to the chain: the destination, the window, the counts per tier, the policy in force and the digest of the package. The record therefore holds, in order and under the hash chain, every time anything left it and under what ceiling. A dry run writes nothing and appends nothing.
5. **What crosses is bounded by the request, overlay included.** The resolution lines a package ships so a reader can name people (RFC 0006) are lines like any other: one above the requested tiers stays home and is counted as held back. Nothing crosses that the request did not ask for, whatever the ceiling.

**Consequences.** The owner's circumstances can change and the record follows: raising a ceiling is one edit to one file, in the record, and the next crossing line shows it took effect. An unattended consumer can be trusted with a fixed command line, because the command cannot exceed the ceiling and cannot let tier 3 through on its own. The circle stays auditable from the record alone: given the crossing lines and the policy file, every bundle is accounted for. The price is that a crossing line is tier 1 and crosses too, so a destination learns when the record last crossed to it and to others; that is data about the record, not about the owner's day, and it is the point.

**Amended by ADR 0022.** The `mcp` entry may also name, under `write`, the write tools an orchestrator may use through the door: `sign_day` (the day's signature) and `note_day` (a note on a day), none by default and none once the entry has expired, within `write_window_days` (60). The ceiling still governs what is read; `write` governs what may be written, and neither ever lets tier 3 through (docs/mcp.md, "Write tools").

**Amended 2026-10-15: the `notion` entry.** `logbook export notion` (docs/export-notion.md) hands the record's facts about people, ideas and orgs to the program that keeps the owner's Notion, and is a crossing like any other: nothing leaves without a `notion` entry, its `max_tier` and `until` hold as every entry's do, tier 3 never leaves for it, and every real run appends one `crossing/v1` line. The signed-day gate of RFC 0034 holds for it as for every crossing, and one key may lift it: an entry that says `"include_unsigned": true` lets `--include-unsigned` hand over the facts of unsigned days too. Neither the key nor the flag alone does, so an unattended consumer with a fixed command line cannot widen what leaves, and an edit to the file alone cannot either. The key is not part of the entry's version, which stays the digest of `max_tier`, `until` and `model`; the folder's manifest and the crossing line say `signed_only` beside it. The lines that bind a name to a key, `resolution/v1` and the `entity/v1` lines of RFC 0037, are this export's overlay, held to the ceiling and not to the signature, as a crossing package ships its resolution lines: an idea's Notion page id or an org's domain bound on an unsigned day is a key the folder may carry, while every fact matched by it rests on signed days.

**Derived material follows the policy, not the head.** What is derived through a crossing (a model's draft of a day, `draft/v1` of RFC 0036, is the first) is held to the entry that let its evidence cross as that entry counts today, not as it counted when the line was written. Lowering a ceiling, passing an `until` or removing an entry appends nothing, so no new line and no moved head says it happened; the readers therefore check, every time: a derived line above the entry's `max_tier` today is shown by no reader (the Day says `superseded by policy` and why, and nothing of its text; the MCP door holds it back like a line above its own ceiling, and counts it), `doctor` lists the days it covers, and the line stays in the record, as every line does. Each derived line records the version of the entry it was made under (`extra.policy_version`: the SHA-256 of the RFC 8785 JSON of the entry's `max_tier`, `until` and `model`), so the writer that made it can tell when the entry changed and make it again under the entry as it is now: `dream --catch-up` dreams a day again when its draft is above the ceiling or was dreamed under another version, superseding the old draft, and dreams nothing under an expired entry ([the dream](../dream.md), *When the entry changes*).

**Amended 2026-10-21: a new record names no one.** The owner's decision of 21 Oct 2026: the program names no destination. `logbook init`, `logbook demo` and the first export into a record without the file write `{"mcp": {"max_tier": 1}}` and nothing else, and a record without the file reads the same; `hermes`, like every other destination, is an entry the owner writes. A record whose file already names `hermes` keeps it: the file is never rewritten.
