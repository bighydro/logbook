# ADR 0016 — The crossing ceiling is the owner's setting; a crossing is never invisible

Status: accepted · 2026-09-29

**Context.** A crossing package (RFC 0005) hands verbatim lines, payloads included, to a named member of the circle. RFC 0005 states the tier policy in prose: tier 1 crosses automatically, tier 2 after a batched review, tier 3 never. Written as a constant in the code, that policy would be wrong twice: too strict for an owner whose circumstances change (a partner who should see the money lines, a doctor who should see the health lines), and too loose the moment anyone edits it, because nothing would then say that the ceiling moved. The first consumer, Hermes, runs nightly and unattended; whatever it can pull must be exactly what the owner meant to let cross, and the record must show every time it crossed.

**Decision.**

1. **The ceiling is a setting in the record, not a constant.** `<root>/policy/crossing.json` maps a destination to the highest tier that may cross to it: `{"hermes": {"max_tier": 2}}`. `logbook init` writes that default; so does the first real export into a record that has none. The code reads the file and never decides a ceiling on its own. A destination the file does not name has no ceiling and cannot receive a crossing until the owner adds it.
2. **Every export names its destination and the tiers it asks for.** `logbook export crossing --to <destination> --tier 1|1,2|1,2,3`. A request above the destination's ceiling exits non-zero with a message that names the file, so the owner raises the ceiling deliberately, in the record, or does not.
3. **Tier 1 crosses by default; tier 2 only when asked; tier 3 only when both the policy allows it and the owner types `--tier 1,2,3`.** A policy edit alone never lets tier 3 cross. When tier 2 crosses, the manifest carries a `review` section listing every tier-2 line in the package by id, kind, source and time, so the batch can be reviewed as a whole (ADR 0005: one message, never line by line). When tier 3 crosses, the manifest and the console say so in words nobody can miss.
4. **A crossing is never invisible.** Every real export appends one `crossing/v1` line (RFC 0011) to the chain: the destination, the window, the counts per tier, the policy in force and the digest of the package. The record therefore holds, in order and under the hash chain, every time anything left it and under what ceiling. A dry run writes nothing and appends nothing.
5. **What crosses is bounded by the request, overlay included.** The resolution lines a package ships so a reader can name people (RFC 0006) are lines like any other: one above the requested tiers stays home and is counted as held back. Nothing crosses that the request did not ask for, whatever the ceiling.

**Consequences.** The owner's circumstances can change and the record follows: raising a ceiling is one edit to one file, in the record, and the next crossing line shows it took effect. An unattended consumer can be trusted with a fixed command line, because the command cannot exceed the ceiling and cannot let tier 3 through on its own. The circle stays auditable from the record alone: given the crossing lines and the policy file, every bundle is accounted for. The price is that a crossing line is tier 1 and crosses too, so a destination learns when the record last crossed to it and to others; that is data about the record, not about the owner's day, and it is the point.
